# 03. 分析并实现微前端加载关键链路

## 这节课只看一件事

主应用到底怎么把子应用接进来。

配套视频会带着把代码敲完，这份文档只保留关键链路和必须看懂的文件。

这一节对应的工程里有 3 个项目：

- `main-app`：主应用
- `order-app`：订单子应用
- `finance-app`：财务子应用

最后要跑通的效果只有 4 个：

- 两个子应用都能独立运行
- 主应用能在订单和财务之间切换
- 子应用内部切页时，主应用地址栏会跟着变
- 从一个子应用切走再切回来，能回到上次停留的位置

---

## 1. 先看整条链路

先把主线记住：

```text
用户点击菜单 / 直接输入 URL
  ↓
主应用根据 URL 判断当前该显示哪个子应用
  ↓
主应用按 manifest 找到子应用入口 entry 和默认路由 defaultPath
  ↓
主应用动态加载子应用的 micro-entry
  ↓
主应用调用 mount({ container, initialPath, hostApi })
  ↓
子应用把自己的页面渲染到主应用容器里
  ↓
子应用内部路由变化后，通过 hostApi 回告主应用
  ↓
主应用更新地址栏，并记住这个子应用上次停留的位置
```

这就是最小微前端的加载关键链路。

---

## 2. 先盯这几个文件

这一节真正要看的，主要就是下面几个文件：

| 文件                              | 负责什么                                           |
| --------------------------------- | -------------------------------------------------- |
| `main-app/src/manifest.js`        | 记录每个子应用的入口地址和默认路由                 |
| `main-app/src/router/index.js`    | 主应用接管地址栏，并从 URL 反推出当前目标子应用    |
| `main-app/src/App.vue`            | 主应用的核心调度：加载、挂载、卸载、切换、同步路由 |
| `order-app/src/micro-entry.js`    | 订单子应用对主应用暴露的接入入口                   |
| `finance-app/src/micro-entry.jsx` | 财务子应用对主应用暴露的接入入口                   |

其他文件先把它们当成普通 SPA 代码就行。

---

## 3. 第一步：主应用先有一份子应用清单

主应用不能凭空知道“订单系统入口在哪”“财务系统默认先显示哪一页”。

所以它手里要先有一份 manifest。

最小版本至少要说明 3 件事：

- 这是谁
- 它的入口地址是什么
- 它的默认路由是什么

这一节里的 manifest 大致长这样：

```js
export const manifest = {
  order: {
    entry: "http://localhost:5174/src/micro-entry.js",
    defaultPath: "/orders/list",
  },
  finance: {
    entry: "http://localhost:5175/src/micro-entry.jsx",
    defaultPath: "/finance/bills",
  },
};
```

这里最容易疑惑的是 `entry` 为什么直接写成一个本地 URL。

原因很简单：Vite 开发服务器会把 `src` 里的模块以 HTTP ESM 的方式暴露出来，所以主应用可以直接去加载子应用的 `micro-entry` 文件。

---

## 4. 第二步：子应用暴露微前端入口

普通 SPA 的启动方式，一般是自己挂到 `#app`。

但微前端场景里，子应用不能再自己决定挂到哪里。

现在是主应用告诉它：

“我给你一个容器，你挂到这里。”

所以子应用要额外暴露一层接入入口，最小协议就是这 3 个方法：

```js
export async function mount({ container, initialPath, hostApi }) {}
export async function navigate(path) {}
export async function unmount() {}
```

- `mount`：主应用让子应用显示出来
- `navigate`：主应用让当前子应用切到指定内部路由
- `unmount`：主应用让子应用从页面里移出去

这里还有一个关键点：

订单和财务两个子应用，内部都用了 memory router。

原因不是因为它更高级，而是因为浏览器地址栏已经交给主应用统一维护了。子应用内部只需要维护自己的内部路由状态，不应该再直接抢地址栏。

还有一个很容易漏掉的细节：

`mount` 时就要把 `initialPath` 先喂给子应用内部路由。这样主应用直达某个深路径，或者切回子应用上次停留页时，子应用才能落到正确页面，而不是每次都退回默认页。

---

## 5. 第三步：主应用先接管地址栏

这一节里，主应用不是点击菜单后直接操作子应用。

它先改的是自己的 URL。

也就是说：

- 菜单点击先 `router.push()`
- 主应用再根据当前 URL 判断目标子应用和目标内部路由
- 后面的加载、挂载、切换，统一交给同一套调度流程处理

这样做的好处是，URL 会变成唯一可信状态来源。

主应用路由层主要做两件事：

- 识别当前路径属于订单还是财务
- 把当前 URL 收敛成统一结构：`appName + childPath`

比如：

- `#/orders/detail/2048` 会被解析成 `order + /orders/detail/2048`
- `#/finance/bills` 会被解析成 `finance + /finance/bills`

这样后面的调度流程才知道现在到底该加载谁。

---

## 6. 第四步：主应用动态加载并挂载子应用

这一步是整条链路的核心。

主应用真正做的事情，不是提前把所有子应用都写死到页面里，而是到了需要显示谁的时候，再去动态加载谁。

主应用里的 `syncToRoute()`，本质上就在做这件事。

### 6.1 如果还是同一个子应用

比如已经在订单系统里，只是从列表页切到详情页。

这时不需要卸载重挂，只要调用当前子应用的 `navigate(childPath)` 就够了。

### 6.2 如果切到了另一个子应用

比如从订单切到财务。

这时顺序是：

1. 先卸载旧子应用
2. 再显示 loading
3. 再动态加载新子应用入口
4. 最后调用新子应用的 `mount()`

这个顺序不能乱。

特别是先 `unmount` 再挂新应用，这一步很重要。否则旧应用还没卸干净，就去改容器内容，后面很容易出问题。

### 6.3 为什么还要做模块缓存

主应用里还有一个 `moduleCache`。

作用很直接：

第一次加载过的子应用入口模块，后面切回来时可以直接复用，不必每次都重新 `import()`。

这样切换会更轻一些。

---

## 7. 第五步：子应用内部切页后，要回告主应用

只做到“主应用能把子应用显示出来”还不够。

因为子应用自己还会继续切内部页面。

比如订单系统会从：

- 列表页
- 切到详情页
- 再切到退款页

如果这些变化不回告主应用，就会有两个直接问题：

- 浏览器地址栏不同步
- 切走再切回来时，很难恢复上次位置

所以主应用在调用 `mount()` 时，会把 `hostApi` 一起传给子应用。

子应用内部路由变化后，要主动调用：

```js
hostApi.onChildRouteChange({ path: to.fullPath });
```

主应用收到以后，再做两件事：

- 更新自己的地址栏
- 记录这个子应用最新停留的内部路由

这就是“子应用负责业务内部切换，主应用负责统一外部地址”的分工。

---

## 8. 第六步：补上两个容易忽略的问题

最小微前端能跑起来以后，还要补两个很关键的稳定性点。

### 8.1 记住每个子应用上次停留的位置

主应用里有一个 `lastVisitedPathByApp`。

它的作用是：

- 订单切走前停在什么页，记下来
- 财务切走前停在什么页，也记下来

这样用户从订单切到财务，再切回订单时，就能回到上次停留页，而不是每次都回默认页。

### 8.2 防止异步竞态把旧结果盖回来

主应用切换子应用不是同步一步完成的。

中间会经过：

- 卸载旧应用
- 动态加载新入口
- 挂载新应用

这几步里只要有异步，就可能出现“用户后点的内容先显示，旧请求晚回来又把它盖回去”的问题。

这一节里用 `switchToken` 处理这个问题。

可以把它理解成一轮切换对应一个版本号。

只要异步结果回来时发现自己已经不是最新版本，这一轮结果就直接丢弃，不再继续改页面。

---

## 9. 小结

这一节最重要的，不是记住某个 API，而是记住这条加载链路：

- 主应用先有 manifest
- 子应用暴露 micro-entry
- 主应用先接管 URL，再决定该加载谁
- 主应用动态 `import()` 子应用入口，并调用 `mount`
- 子应用内部切页后，再通过 `hostApi` 回告主应用
- 主应用负责更新地址栏、记住上次位置，并处理切换竞态

这条链路看明白了，后面再看微前端框架，就不会只剩下“配配置”和“抄 API”。
