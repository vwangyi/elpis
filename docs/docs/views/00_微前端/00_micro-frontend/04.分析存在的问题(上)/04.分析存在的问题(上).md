# 04. 分析存在的问题(上)

---

## 1. 问题一：样式作用域还是全局的

主应用能把子应用挂进来，不代表子应用的 CSS 已经被隔离开了。

只要子应用样式还在改这些选择器：

- `:root`
- `body`
- `#app`

它改的就不是“自己那一块”，而是整张页面。

这就是为什么微前端里很容易出现这些现象：

- 主应用字体被带偏
- 颜色变量被覆盖
- 页面背景被子应用改掉
- 两个子应用切换后，视觉风格互相串味

这一节里先记住两个判断。

第一，当前这套实现里问题没有完全放大，不代表它不存在。

第二，光靠“大家命名小心一点”不够，因为真正麻烦的往往就是 `body`、`:root`、全局 reset 和 CSS 变量。

后面框架通常会从两边接这个问题：

- 给子应用样式补作用域
- 用更硬的隔离边界，比如 Shadow DOM

解决方案：

- 子应用样式只作用于自己的根容器，不直接改 `html`、`body`、`:root`、`#app`
- 全局 reset、主题变量和页面级样式由主应用统一管理，不交给各个子应用各自处理
- 复杂场景采用运行时样式隔离或 Shadow DOM，把样式边界真正落到子应用容器上

---

## 2. 问题二：JS 全局对象和全局副作用会互相污染

样式之外，还有一层更麻烦的问题：运行时上下文是共享的。

现在订单和财务虽然已经是两个子应用，但它们还跑在同一张页面里，所以天然共享：

- `window`
- `document`
- `history`

这意味着污染的不只是 `window.xxx`。

还包括：

- `document.title`
- 全局事件监听器
- 定时器
- 改写过的全局函数
- 直接挂到 `body` 的浮层节点

这一点要特别注意：

`unmount()` 只能把当前应用树卸掉，不等于所有全局副作用都会自动回滚。

也就是说，应用节点没了，不代表这些东西也一起消失：

- 写到全局对象上的值
- 没清掉的监听器
- 没清掉的定时器
- 直接挂到全局页面上的 DOM

所以后面框架做沙箱，不是在制造神秘功能，而是在解决一件很实际的事：

别让所有子应用都直接操作同一个真实 `window`。

解决方案：

- 用代理或沙箱把子应用和真实 `window` 隔开：子应用优先读写自己的运行时上下文，只有缺失能力时再回退到真实浏览器对象
- 对 `addEventListener`、定时器、补丁函数这类全局副作用建立登记表，子应用卸载时统一回收，避免残留监听器和脏状态
- 弹窗、抽屉、消息提示这类跨层 DOM 不直接裸挂 `body`，而是统一挂到主应用约定的浮层容器，并纳入清理规则
- 如果要上框架，就重点看它有没有把 `window` 沙箱和副作用回收做成运行时能力

## 3. 问题三：主应用知道得太多

上一节里的手写版是这样接子应用的：

- 主应用在 manifest 里写死子应用入口地址
- 主应用直接 `import()` 那个 `micro-entry`
- 主应用默认它一定会暴露 `mount / unmount / navigate`

这套写法在当前实现里可以跑通。

但它有一个明显前提：主应用知道了太多子应用实现细节。

真实项目里，主应用不应该继续去猜这些东西：

- 入口文件名到底叫什么
- 构建后真实文件路径是什么
- 后续 chunk 去哪里找
- 样式、字体、图片按什么基准路径加载

所以后面真正要解决的，不是“再多写一个 JS 地址”。

而是让子应用把自己的入口说明清楚，再由主应用去解析整份资源入口。

这也是后面会出现 HTML Entry、资源解析、运行时 `publicPath` 这些能力的原因。

先记一句话就够了：

当前这套实现里可以直接写 `micro-entry.js`，但真实项目里主应用不该长期知道这么多。

解决方案：

- 主应用不再直接猜某个 JS 文件名，而是读取子应用提供的入口 HTML 或完整入口描述
- 运行时先解析入口 HTML，再拆出模板、样式、脚本，先把模板放进容器，再加载样式和脚本，最后从真正的 entry script 里拿到 `mount()`
- 用专门的资源加载器处理这条链路，像 `import-html-entry` 这一类能力，本质上就是把“解析 HTML 并执行入口脚本”标准化
- 再配合运行时 `publicPath` 统一修正 chunk、图片、字体、CSS 和部署路径，避免一构建、一上 CDN 就失效

---

## 4. 小结

上半部分的 3 个问题，本质上都在说明一件事：

我们现在只是把子应用“接进来了”，还没有真正把边界“管起来”。

- CSS 还可能打到全局
- JS 还共享同一个真实浏览器上下文
- 主应用还在替子应用维护太多实现细节

后面看框架时，要重点对回这 3 类能力：样式隔离、运行时沙箱、入口与资源加载。
