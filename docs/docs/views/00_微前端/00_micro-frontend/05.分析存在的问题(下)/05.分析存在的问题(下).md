# 05. 分析存在的问题(下)

---

## 1. 问题四：通信方式太原始

上一节里，主应用和子应用之间主要靠 `hostApi` 通信。

这在当前实现里够用，因为当时只需要两件事：

- 子应用挂载完成后通知主应用
- 子应用内部路由变化后回告主应用

但真实项目里还会继续同步很多跨应用信息，比如：

- 当前租户
- 主题
- 未读数
- 权限
- 登录态

如果还继续在 `hostApi` 上一条条加回调，很快就会出现两个问题：

- 主应用知道越来越多子应用细节
- 接口越加越长，主子应用耦合越来越重

所以后面更稳的方向，不是继续堆业务专用回调，而是把跨应用公共信息收成一条共享状态通道。

可以先把它理解成：

- 有一份共享状态
- 大家都能读
- 状态变了会统一通知订阅者

但也要记住一个边界：共享状态不是公共垃圾桶。只有真正跨应用共享的信息，才适合放进去。

解决方案：

- 不再继续堆业务专用回调，而是把跨应用公共信息收成一条共享状态通道：底层是“共享状态容器 + 发布订阅机制”
- 这条通道至少要有清晰的几个动作：初始化公共状态、订阅状态变化、更新状态、取消订阅；如果有后挂载的子应用，还要能读取当前快照
- 状态更新尽量按 patch 合并，而不是每次整包重写，谁只改自己的字段，就只提交自己的变更
- 订阅关系必须跟生命周期绑定，子应用卸载时及时退订，避免重复回调和内存泄漏
- 严格限制共享状态范围，只放租户、主题、未读数这类跨应用公共信息，不把页面内部状态塞进去

## 2. 问题五：工程兜底还不够

当前手写版已经有最基本的兜底：

- loading
- error
- `try / catch`

这说明主应用已经知道“加载子应用可能失败”。

但真实项目里，问题会继续变多：

- 资源加载太慢，要不要超时
- 失败后要不要重试
- 脚本执行时报错怎么办
- 全局异常怎么统一收集
- 没打开的子应用要不要预加载
- 远程资源请求要不要自定义 `fetch`

这些问题一多，就不再是“补几个 if”这么简单。

这也是为什么框架后面会提供这些能力：

- 生命周期钩子
- 全局异常处理
- 预加载
- 自定义资源拉取

框架的价值，不只是帮你 `mount()`，也是在帮你接这些工程细节。

解决方案：

- 给加载流程补齐超时、重试、降级和失败兜底策略
- 把资源加载错误、脚本执行错误和生命周期异常统一收集与上报
- 对高频子应用做预加载，并统一处理 `fetch`、Cookie 和跨域资源策略

## 3. 问题六：记住路由，不等于真正的保活

现在主应用已经能记住每个子应用上次停留的路由。

这当然是体验提升，但它还不等于真正的保活。

因为现在切换应用时，旧子应用还是会真的执行 `unmount()`。

这就意味着这些东西并没有被保住：

- 组件实例
- 表单输入
- 滚动位置
- 已加载的数据
- 弹窗状态

所以“记住上次地址”只解决了返回到哪一页的问题。

它没有解决这些更细的体验问题：

- 切回来还要不要重新拉数据
- 切回来表单内容还在不在
- 滚动条能不能停在原来的位置
- 能不能真的缓存整个子应用实例

这也是为什么一旦业务更复杂，团队很快就会继续往更重的运行时管理或框架能力上走。

解决方案：

- 先明确哪些页面只需要路由恢复，哪些页面需要真正的实例保活
- 需要保活的子应用保留实例或缓存数据，而不是每次切换都重新创建
- 切回时同步恢复滚动位置、表单输入、弹窗状态和列表状态

## 4. 问题七：子应用里如果再套 iframe，边界会再多一层

这一点在真实项目里非常常见。

因为子应用内部还可能继续接这些内容：

- BI 报表
- 第三方平台页面
- 文档预览
- 暂时还没改造的老系统

这时候虽然外层已经用了微前端，但子应用内部一旦再套 iframe，浏览器就会重新切出一层独立上下文。

最直接的影响就是：

- iframe 有自己的 `window`
- iframe 有自己的 `document`
- iframe 有自己的路由和滚动区域
- iframe 里的变化不会自动同步到外层

于是又会冒出一批具体问题：

- 外层不知道 iframe 里当前停在哪个页面
- 内容高度变了，外层不一定会自动调高
- 容易出现双层滚动
- 真要通信时，还是得回到 `postMessage`

这里要记住一句话：

微前端框架能管的是“主应用接子应用”这一层，不会自动抹平子应用内部 iframe 自己那层浏览器边界。

只要里面继续有 iframe，这层桥接和同步就还得自己设计。

解决方案：

- 为 iframe 设计显式桥接协议，用消息同步内部路径、页面高度和关键状态
- 明确外层页面和 iframe 内页面各自负责的交互边界，比如弹窗、下载和登录跳转
- 能直接改造成普通子应用能力的部分，优先去掉 iframe 这一层边界

## 5. 小结

| 边界问题            | 我们现在的手写版                                             | 后面框架一般会先接住什么                                | 还剩什么要你自己判断                                         |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------- | ------------------------------------------------------------ |
| 样式作用域          | 还会碰 `:root`、`body`、`#app` 这些全局根节点                | 样式命名空间、运行时样式作用域、Shadow DOM 类隔离       | UI 组件库全局 reset、CSS 变量策略、主应用自身样式规范        |
| JS 全局对象和副作用 | 多个子应用共享真实 `window`、`document`，Teleport 也可能直挂全局 | `window` 沙箱、副作用回收、全局容器挂载约束             | `document`、`body`、全局事件、定时器、第三方脚本副作用回收   |
| 入口发现和资源加载  | 主应用写死 `micro-entry.js`，默认能直接 `import()`，还替子应用猜路径 | HTML Entry、资源解析、入口脚本识别、运行时 `publicPath` | 部署路径、CDN、CORS、异常 HTML、ESM 适配                     |
| 通信                | 主要靠 `hostApi` 点对点回调                                  | `props`、共享状态通道、生命周期里的订阅/退订            | 领域边界怎么划、哪些状态该共享、别把全局状态当垃圾桶         |
| 错误处理和预加载    | `try / catch`、loading、error 还比较薄                       | 生命周期钩子、全局异常处理、`prefetch`、自定义 `fetch`  | 超时、重试、监控归因、降级策略                               |
| 保活                | 目前只记住路由字符串                                         | 框架能帮你把生命周期调度得更稳定                        | 真缓存实例、表单状态、滚动位置、数据恢复仍要自己设计         |
| 子应用里再套 iframe | 这一层边界目前完全没接                                       | 外层主应用和子应用的接入边界能先被框架管理              | `postMessage`、高度同步、登录态联动、下载/新窗口回传、跨域限制 |
