# 10. 沙箱

## 这节课要拿到什么结果

这一课只解决一个问题：子应用的 JS 明明在主应用页面里执行，为什么它写 `window.xxx` 时，不一定会污染主应用和其他子应用？

先记住一句话：

```txt
qiankun 的沙箱重点不是让子应用消失在另一个浏览器里，而是让子应用访问 window 时先经过一层代理。
```

你要拿到 4 个结论：

- 微前端沙箱主要处理 JS 运行时隔离，尤其是 `window` 普通字段污染
- qiankun 现代主线是代理沙箱，也就是 `ProxySandbox`
- 只创建代理对象还不够，还要把子应用脚本文本包装后再执行
- 沙箱不是完整浏览器隔离，`document`、存储、事件、定时器、CSS 还需要额外治理

---

## 1. 为什么微前端需要沙箱

先说白话：

多个子应用接进同一个主应用页面后，它们并不是各自拿到一个独立浏览器。它们的 JS 最终还是在同一个页面环境里跑。

也就是说，它们都可能接触到：

- `window`
- `document`
- `setTimeout`
- 全局事件
- 浏览器存储

如果两个子应用都直接写真实 `window`：

```js
window.sharedRuntime = "order-app";
window.sharedRuntime = "finance-app";
```

后写的人就可能覆盖先写的人。

术语说：

```txt
微前端沙箱要解决的是运行时隔离问题，重点是收住全局对象污染和部分全局副作用。
```

这里要分清楚：

```txt
window 普通字段污染：沙箱重点处理。
document、localStorage、全局事件、定时器：沙箱只能处理一部分。
CSS 污染：不是 JS 沙箱主线，通常要靠样式隔离。
```

---

## 2. 代理沙箱的核心思路

先不看 qiankun 源码，先看思路。

子应用经常会把自己的入口或运行数据挂到 `window` 上：

```js
window.orderApp = {
  mount(container) {},
  unmount(container) {},
};

window.sharedRuntime = "order-app";
```

如果这段代码直接执行，写到的就是真实浏览器 `window`。

代理沙箱的想法是：

```txt
不要直接把真实 window 给子应用。
给它一个看起来像 window 的代理对象。
子应用写 window.xxx 时，实际先写到自己的 fakeWindow。
```

可以先用两个名字理解：

- `fakeWindow`：一个普通对象，用来保存子应用自己写入的全局字段
- `proxyWindow`：一层代理，用来决定这次读写应该走 `fakeWindow` 还是真实 `window`

最小模型大概是这样：

```js
function createProxyWindow(realWindow) {
  const fakeWindow = Object.create(null);
  let proxyWindow = null;

  proxyWindow = new Proxy(fakeWindow, {
    get(target, key) {
      if (key === "window" || key === "self" || key === "globalThis") {
        return proxyWindow;
      }

      if (key in target) {
        return target[key];
      }

      return realWindow[key];
    },

    set(target, key, value) {
      target[key] = value;
      return true;
    },
  });

  return proxyWindow;
}
```

这段代码做了三件事。

第一，子应用写入的字段进 `fakeWindow`：

```js
proxyWindow.sharedRuntime = "order-app";
```

实际保存到的是：

```js
fakeWindow.sharedRuntime = "order-app";
```

第二，读取时先读 `fakeWindow`。如果子应用自己写过，就读自己的值；如果没写过，再去真实 `window` 上找浏览器原本的能力。

第三，`window`、`self`、`globalThis` 都返回 `proxyWindow`。否则代码可能这样绕出去：

```js
window.window.sharedRuntime = "order-app";
```

入口漏了，沙箱就漏了。

## 3. 只创建 proxyWindow 还不够

现在有了 `proxyWindow`，问题还没结束。

真实子应用代码一般不会写：

```js
proxyWindow.sharedRuntime = "order-app";
```

它更可能写：

```js
window.sharedRuntime = "order-app";
```

如果浏览器直接执行这段脚本，里面的 `window` 仍然是真实 `window`。所以沙箱要做两层事：

```txt
第一层：准备 proxyWindow，用它接住子应用对 window 的读写。
第二层：改变子应用脚本的执行方式，让脚本里的 window 指向 proxyWindow。
```

少了第一层，没有对象能接住写入。

少了第二层，子应用脚本根本不会用这个代理对象。

---

## 4. 子应用脚本怎么进入沙箱

主应用加载子应用时，常见情况是先拿到一段 JS 文本。

字符串不会自己执行，所以框架需要执行这段文本。最小模型里可以用间接 `eval` 表达这个动作：

```js
(0, eval)(code);
```

这里先把结论说清楚：

```txt
eval 只负责执行字符串代码，它本身不是沙箱。
真正形成沙箱边界的是 proxyWindow 和执行前的函数包装。
```

框架会把子应用脚本文本包进一个函数：

```js
function createExecutableScript(scriptText) {
  return `;(function(window, self, globalThis) {
${scriptText}
}).bind(window.proxy)(window.proxy, window.proxy, window.proxy);`;
}
```

拆开看就是：

```js
(function (window, self, globalThis) {
  // 子应用脚本文本
}).bind(window.proxy)(window.proxy, window.proxy, window.proxy);
```

这段包装做了几件事：

- 函数参数名故意叫 `window`、`self`、`globalThis`
- 调用时把三个参数都传成 `window.proxy`
- `.bind(window.proxy)` 尽量让函数里的 `this` 也指向代理对象

所以子应用虽然还是写：

```js
window.orderApp = { mount() {} };
window.sharedRuntime = "order-app";
```

但实际效果更接近：

```js
proxyWindow.orderApp = { mount() {} };
proxyWindow.sharedRuntime = "order-app";
```

这就是“子应用 JS 运行在沙箱环境中”的关键。

## 5. 为什么会看到 with

有些旧代码不会写 `window.xxx`，而是直接写：

```js
myVar = "子应用变量";
document.title = "订单系统";
setTimeout(() => {});
```

这种写法叫隐式全局访问。它没有明确说“我要访问 `window.myVar`”。

为了让这类访问也尽量进入代理对象，框架里可能会出现 `with`：

```js
(function (window, self, globalThis) {
  with (window) {
    // 子应用脚本
  }
}).bind(window.proxy)(window.proxy, window.proxy, window.proxy);
```

先说白话：

`with(window)` 会把 `window` 放到变量查找的前面。代码在里面找变量时，会先尝试从这个对象上找。

在 qiankun 的包装里，这里的 `window` 已经是 `proxyWindow`，所以隐式变量也会更容易走到代理层。

它通常还要配合 `Proxy` 的 `has` 拦截。否则有些变量查找可能会跳出代理对象，直接去真实全局作用域找。

注意：

```txt
with 不是推荐业务代码使用的语法。
这里是框架为了兼容历史脚本和隐式全局写法，在运行时包装层里使用。
```

## 6. qiankun 实际链路怎么理解

可以把 qiankun 的沙箱链路理解成这样：

```txt
qiankun 加载子应用 HTML
  -> 提取里面的 script
  -> 拿到子应用脚本文本
  -> 创建 proxy window
  -> 把脚本文本包装成函数
  -> 执行时把 proxy window 传成 window/self/globalThis
```

所以面试里如果只说“qiankun 用了 Proxy”，是不够完整的。

更准确的说法是：

```txt
qiankun 创建 proxy window，再把子应用脚本文本包进函数。执行时把 proxy window 作为 window、self、globalThis 传进去。这样子应用代码里写的 window.xxx，会进入自己的代理环境，而不是直接写真实 window。
```

## 7. 这一课讲的是哪种沙箱

前端里经常会听到几种“沙箱”。它们不是一回事。

### 7.1 代理沙箱

白话解释：

```txt
不给子应用真实 window，而是给它一个代理 window。
子应用以为自己在写 window，其实先写进 fakeWindow。
```

qiankun 在现代浏览器里的主线就是代理沙箱，也就是 `ProxySandbox`。

这一课前面讲的这些都属于代理沙箱：

- `fakeWindow`
- `proxyWindow`
- `new Proxy(...)`
- `window/self/globalThis` 指向代理对象
- 子应用脚本文本包装执行

### 7.2 快照沙箱

白话解释：

```txt
你先写真实 window，等你离开时，我再把 window 恢复回去。
```

快照沙箱一般做三件事：

```txt
子应用激活前，记录 window 当前有哪些字段和值。
子应用运行时，允许它写真实 window。
子应用失活时，对比变化，把改过的内容尽量恢复。
```

它更像“进入前记账，离开后还账”。

它适合旧浏览器或同一时间只运行一个子应用的场景，不适合多个子应用同时运行。因为多个应用都在改真实 `window` 时，恢复顺序很容易互相影响。

### 7.3 iframe 沙箱

白话解释：

```txt
代理沙箱还在同一个页面里管理 window。
iframe 沙箱直接给子应用一个浏览器隔离出来的小页面。
```

iframe 里天然有自己的：

- `window`
- `document`
- DOM 树
- CSS 作用范围
- JavaScript 全局环境

所以 iframe 隔离更强，但和主应用融合更麻烦。

常见问题包括：

- 路由同步要额外处理
- 通信通常要靠 `postMessage`
- 弹窗、滚动、高度、主题、权限、埋点都更难统一

qiankun 的主线不是 iframe 沙箱。它更想让子应用像同一个页面的一部分，所以选择代理沙箱作为现代主线。

## 8. qiankun、MicroApp、无界的沙箱路线

这几个框架不要混着记。

```txt
qiankun：主线是代理沙箱，不以 iframe 承载子应用运行时。
MicroApp：默认是 with 沙箱，也支持切换到 iframe 沙箱。
无界：核心设计之一是 WebComponent 容器 + iframe 沙箱。
```

所以不能笼统地说“微前端沙箱就是 Proxy”，也不能笼统地说“微前端沙箱就是 iframe”。

更准确的判断是：

```txt
不同框架在页面融合和隔离强度之间取舍不同。
qiankun 更偏页面融合，所以主线是代理沙箱。
无界更强调原生隔离，所以把 iframe 沙箱放进核心架构。
```

## 9. 沙箱能管什么，不能管什么

这里说的沙箱，主要指 qiankun 这种 JS 运行时沙箱。

它比较擅长处理：

- `window` 普通字段污染
- 多个子应用写同名全局变量
- 子应用读取自己写过的全局状态
- 子应用脚本执行时的 `window` 指向问题
- 失活时恢复一部分全局变量变化

但它不能当成完整浏览器隔离。

下面这些不能全靠 JS 沙箱兜底：

- `document.title`
- `document.body`
- `localStorage` / `sessionStorage`
- Cookie / IndexedDB
- 网络请求
- 全局事件监听
- 定时器
- WebSocket
- 挂到 `body` 上的弹窗
- CSS 样式污染

这些问题要靠卸载清理、命名规范、样式隔离、iframe 或其他机制配合。

一句话：

```txt
qiankun 沙箱主要解决 JS 运行时的全局对象污染，不等于完整浏览器隔离。
```

## 10. 真实业务里什么时候需要沙箱

判断标准很简单：

```txt
只要你要运行一段不是当前页面完全可信、完全受控的代码，就应该考虑沙箱。
```

常见场景包括：

- 微前端：多个团队的子应用进入同一个主应用页面
- 低代码平台：用户写表达式、自定义动作或校验规则
- 在线代码预览：用户输入代码后要在页面里运行
- 插件系统：第三方插件要拿到能力，但不能无限制改平台
- 第三方脚本：统计、客服、广告、A/B 实验脚本可能改 DOM 或写全局变量

沙箱不是微前端专属能力。它本质上是一种边界设计：允许代码运行，但把能影响外部环境的范围收住。

## 11. 几种沙箱机制怎么选

可以按这张表理解：

```txt
想让子应用像同一个页面的一部分：优先理解代理沙箱。
只需要单实例激活后的全局变量恢复：理解快照沙箱。
需要浏览器级强隔离：考虑 iframe 沙箱。
只运行计算逻辑，不碰 DOM：考虑 Web Worker。
只开放有限表达式能力：考虑解释器或受限 DSL。
要运行高风险代码：考虑服务端、容器或独立域名隔离。
```

对 qiankun 这条线来说，重点还是代理沙箱。

它的优势是融合度高：主应用可以统一布局、路由、通信和生命周期。

它的代价是隔离不彻底：`document`、存储、事件、定时器、网络请求、CSS 仍然需要额外治理。

所以核心判断不是“哪种沙箱最好”，而是：

```txt
你要的是页面融合，还是强隔离。
```

## 12. 面试里问 qiankun 沙箱，怎么答

可以按这个顺序答。

第一，为什么需要沙箱：

```txt
微前端里多个子应用共享一个浏览器页面。
如果子应用直接写真实 window，就可能污染主应用和其他子应用。
```

第二，怎么隔离 `window`：

```txt
qiankun 会创建 proxy window。
子应用写 window.xxx 时，优先写到自己的 fakeWindow。
子应用读 window.xxx 时，也优先从自己的 fakeWindow 读，没有再读真实 window。
```

第三，子应用 JS 怎么进入沙箱：

```txt
qiankun 通过 HTML Entry 拿到子应用 script。
执行前把脚本文本包成函数。
执行时把 proxy window 作为 window/self/globalThis 传进去。
必要时配合 with，让隐式全局变量也尽量走代理。
```

第四，沙箱类型：

```txt
现代浏览器主线是 ProxySandbox。
LegacySandbox 是基于 Proxy 的单实例恢复型沙箱。
没有 Proxy 时，会退到 SnapshotSandbox 这类快照恢复思路。
iframe 沙箱是浏览器原生隔离，但不是 qiankun 的主线。
```

第五，边界：

```txt
沙箱主要处理 JS 全局变量污染。
它不是 iframe，不能完整隔离 document、localStorage、定时器、全局事件、网络请求和 CSS。
这些要靠卸载清理、命名规范、样式隔离、iframe 或其他机制配合。
```
