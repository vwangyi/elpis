# 路由处理

## 这节内容要解决什么问题

这一节不是只给学生一个“能跑”的修复，而是让学生理解：微前端里的路由问题，本质上不是某一个路由 API 写错了，而是多个应用共享同一个浏览器环境以后，谁来管理地址栏、谁来管理路由状态的问题。

本节要带学生拿到 4 个结论：

1. 为什么切换子应用和子应用内部路由时，会出现 `localhost:5173undefined/` 这种错误。
2. 为什么使用 memory router 可以先把错误止住。
3. memory router 解决了什么，又牺牲了什么。
4. 企业项目里会根据不同场景选择不同方案，而不是所有项目都套同一种写法。

最后本节选择两种方案作为后续代码演示：

- 方案一：Memory Router + 主应用统一导航
- 方案二：所有应用统一使用 History + Base/Basename

不过这两种方案的展示方式不一样。

当前项目是混合技术栈：主应用和订单子应用使用 Vue Router，财务子应用使用 React Router。这个组合下，最终稳定实现优先选择“Memory Router + 主应用统一导航”。

“History + Base/Basename”仍然要讲，而且很重要，但它更适合作为新项目、同路由生态或有统一路由封装时的方案来讲。它解决的是 URL 命名空间问题，不自动解决不同路由库共享 `history.state` 的问题。

其他方案只讲实现思路，不在本节完整落代码。

---

## 1. 先复现问题

课堂上先不要急着改代码，先让学生看到问题是怎么发生的。

操作步骤：

1. 启动主应用、订单子应用、财务子应用。
2. 打开主应用：`http://localhost:5173`。
3. 进入订单子应用，比如 `/orders/list`。
4. 在订单子应用内部切换到订单详情或退款处理。
5. 切换到财务子应用。
6. 在财务子应用内部切换到退款打款，比如 `/finance/refund/1024`。
7. 再点击主应用侧边栏里的订单子应用。

此时控制台可能出现类似错误：

```txt
[Vue Router warn]: Error with push/replace State SecurityError:
Failed to execute 'replaceState' on 'History':
A history state object with URL 'http://localhost:5173undefined/' cannot be created
in a document with origin 'http://localhost:5173'
and URL 'http://localhost:5173/finance/refund/1024'.
```

这段错误可以先用白话解释：

浏览器发现路由库想把地址改成一个不合法的地址，里面出现了 `undefined`，所以浏览器拒绝了这次 `replaceState` 操作。

再说术语：

这是多个路由系统共享同一个 `window.history` 时产生的 history state 冲突。主应用的 Vue Router 和子应用里的路由库都在操作浏览器历史记录，但它们写入 `history.state` 的数据结构不一样。

这里要特别注意：不是只有 browser history 会操作 `window.history`，hash router 也可能操作。hash 路由只是把业务路径放到 `#` 后面，并不等于它完全绕开了浏览器 History API。

---

## 2. 为什么会报错

先给学生建立一个基本事实：

微前端不是给每个子应用复制一个浏览器。无论页面里挂了几个子应用，浏览器地址栏只有一个，`window.history` 也只有一份。

当前项目里有 3 套路由：

- 主应用：Vue Router，使用 history 模式
- 订单子应用：Vue Router，原来使用 hash 模式
- 财务子应用：React Router，可能使用 browser history，也可能临时改成 hash history

这里不要误解成“只有主应用和财务子应用有问题，订单子应用没有参与”。订单子应用的 hash 路由也在这条链路里起作用。进一步说，即使把财务子应用也改成 hash 路由，问题仍然可能出现。

原因是：Vue Router 的 `createWebHashHistory()` 虽然名字里有 hash，但它并不是完全不碰浏览器 history。它初始化和跳转时，仍然可能调用浏览器的 `history.replaceState()` 来修正地址，只是它把子路由信息放在 `#` 后面。

React Router 的 `createHashRouter()` 也是同理。它会从 `window.location.hash` 里读取路由路径，但内部跳转时仍然会通过 `window.history.pushState()` 或 `window.history.replaceState()` 更新浏览器历史记录，并写入 React Router 自己需要的 `history.state`，比如 `usr`、`key`、`idx`。

所以 hash 路由解决的是“路径放在哪里”的问题，不是“谁来拥有 `window.history.state`”的问题。

所以原始问题可以拆成 3 层看：

1. 主应用 Vue Router 使用 history，负责 `/orders` 和 `/finance` 这些一级路径。
2. 订单子应用 Vue Router 使用 hash，但嵌入主应用以后，它仍然运行在 `http://localhost:5173` 这个主应用页面里，也会参与浏览器 history 的修正。
3. 财务子应用 React Router 无论使用 browser history 还是 hash history，只要它使用的是 URL-based router，内部跳转时都可能把 `window.history.state` 改成 React Router 自己的数据结构。

也就是说，订单子应用的 hash 路由是“混合路由环境”的一部分，它会让问题更容易暴露；财务子应用只要继续使用会写浏览器 history 的路由模式，不管是 browser router 还是 hash router，都可能成为覆盖主应用 `history.state` 的那一步。

问题发生时，主应用 Vue Router 写入的 `window.history.state` 大致是这样的：

```js
{
  back: null,
  current: "/orders/list",
  forward: null,
  position: 4,
  replaced: true,
  scroll: null
}
```

这些字段是 Vue Router 自己用来维护路由跳转、前进后退、滚动恢复的。

但是财务子应用内部切路由时，React Router 会写入另一种结构。这里不要求它一定是 browser router，`createHashRouter()` 也会写入类似结构：

```js
{
  usr: null,
  key: "xxx",
  idx: 1
}
```

这些字段是 React Router 自己用来维护导航状态的。

于是问题来了：

主应用 Vue Router 以为 `history.state` 还是自己那套结构，可是财务子应用 React Router 已经把它覆盖成了另一套结构。等主应用再次执行跳转时，Vue Router 拿不到自己需要的 `current`、`position` 等字段，就可能在内部拼出 `undefined/`，最终触发浏览器的 `SecurityError`。

再把订单子应用放回这条链路里看，过程会更完整：

1. 订单子应用原本用 hash 路由，嵌入主应用时仍然会根据当前浏览器地址初始化自己的路由。
2. 切到财务子应用后，订单子应用被卸载，财务子应用开始接管页面内容。
3. 财务子应用内部跳转时，即使使用 hash router，也会写入自己的 `history.state`，覆盖了主应用 Vue Router 原本需要的状态字段。
4. 再点击主应用里的订单入口时，主应用 Vue Router 先要把地址从 `/finance/refund/1024` 切回 `/orders/list`。
5. 但这时主应用 Vue Router 读取到的 history state 已经不是自己的结构，于是导航过程中出现 `undefined/`。

所以这不是“hash 路由完全没关系”，也不是“只要都改成 hash 就一定安全”。更准确地说：hash router 仍然是 URL-based router，它仍然可能写 `window.history.state`。当前报错的根本原因，是多个路由实例都在同一个浏览器页面里拥有并改写 `window.history`；主应用 Vue Router 是最终报错的地方。

这里要提醒学生：

不要把问题理解成“React Router 有错”或“Vue Router 有错”。两个路由库在独立应用里都没问题，问题出在微前端嵌入以后，它们开始共享同一个浏览器 history。

也不要把问题理解成“qiankun 做不到不同框架切路由”。qiankun 能做的是根据 URL 和 `activeRule` 加载、挂载、卸载不同框架的子应用。它不会自动统一 Vue Router 和 React Router 写入 `window.history.state` 的内部数据结构。

换句话说：qiankun 负责“当前 URL 应该激活哪个子应用”，但不会替所有路由库决定“谁拥有浏览器 history、谁维护 history state”。这个边界要由项目自己的路由方案来设计。

## 3. 第一种处理：Memory Router 止血

这一步先讲最容易理解的隔离方案。

白话解释：

既然多个子应用一起改浏览器地址会打架，那我们先让子应用在嵌入主应用时不要直接改浏览器地址。子应用内部自己维护一份内存里的路由状态，页面可以切换，但它不再写 `window.history`。

术语解释：

这就是 memory router。它不依赖浏览器地址栏，而是把路由记录保存在 JavaScript 内存里。

当前项目中，止血思路是：

- 主应用仍然使用 `createWebHistory()`。
- 订单子应用独立运行时继续用自己的原路由模式。
- 订单子应用被 qiankun 挂载时改用 `createMemoryHistory()`。
- 财务子应用独立运行时继续用 `createBrowserRouter()`。
- 财务子应用被 qiankun 挂载时改用 `createMemoryRouter()`。

这样做以后，子应用内部路由不再覆盖主应用的 `window.history.state`，控制台里的 `replaceState` 报错就会消失。

这一步可以让学生修改这些文件：

- `order-app/src/main.js`
- `finance-app/src/router.jsx`
- `finance-app/src/main.jsx`

讲解时重点不是让学生背 API，而是让学生知道：

memory router 的作用是把子应用路由和浏览器 history 隔离开。

### 3.1 课堂演示顺序

这一段建议按“先让学生看到错误，再一层层隔离”的顺序讲。

演示顺序：

1. 保持主应用不动，先让学生复现 `replaceState` 报错。
2. 先改订单子应用，让订单在嵌入态使用 memory router。
3. 再改财务子应用，让财务在嵌入态使用 memory router。
4. 再次执行同样的切换流程，观察控制台报错消失。
5. 最后提醒学生：这一步只是止血，地址栏同步问题放到后面“主应用统一导航”里解决。

这一步不要一上来就讲“最终企业方案”，否则学生会看不到 memory router 到底解决了哪一层问题。

### 3.2 第一步：改订单子应用

文件位置：`order-app/src/main.js`

修改方式：`局部修改`

先把 Vue Router 的 memory history 引进来。

原来是：

```js
import { createWebHashHistory } from "vue-router";
```

改成：

```js
import { createMemoryHistory, createWebHashHistory } from "vue-router";
```

如果当前代码已经临时改成了 `createWebHistory()`，这里也可以保留独立运行的原路由模式，但嵌入态一定要切到 `createMemoryHistory()`。

这一节基于项目最原始的路由写法来改：订单子应用内部路由仍然是 `/orders/list`、`/orders/detail/2048`、`/orders/refund/1024`，暂时不做 base/basename 改造。

然后在 `render(props = {})` 里，把创建路由的代码改成：

```js
const history = window.__POWERED_BY_QIANKUN__
  ? createMemoryHistory()
  : createWebHashHistory();

router = createOrderRouter(history);

if (window.__POWERED_BY_QIANKUN__) {
  router.push(window.location.pathname || "/orders/list");
}
```

这段代码要给学生解释清楚：

- `window.__POWERED_BY_QIANKUN__` 用来判断当前是否被主应用嵌入。
- 独立运行时继续用原来的浏览器路由。
- 嵌入主应用时使用 `createMemoryHistory()`，这样订单子应用不会再写浏览器 `window.history`。
- `router.push(window.location.pathname || "/orders/list")` 是把当前主应用地址同步给订单子应用的 memory router。

例如：

```txt
/orders/list          -> 订单列表
/orders/detail/2048   -> 订单详情
/orders/refund/1024   -> 退款处理
```

这里可以顺便提醒学生：

memory router 不读浏览器地址栏，所以嵌入态下需要我们手动告诉它“当前应该显示哪个内部页面”。这就是 `router.push(...)` 的作用。

这里先不要把 `/orders` 前缀去掉。因为原始订单子应用的路由表本来就写的是完整路径。如果这里提前把 `/orders/list` 转成 `/list`，反而会匹配不到原来的订单路由。

### 3.3 第二步：改财务子应用路由创建函数

文件位置：`finance-app/src/router.jsx`

修改方式：`局部修改`

先引入 `createMemoryRouter`。

```js
import {
  createBrowserRouter,
  createMemoryRouter,
  Navigate,
} from "react-router-dom";
```

然后把 `createFinanceRouter()` 改成支持两种模式：

```js
export function createFinanceRouter(options = {}) {
  const { memory = false, initialPath = defaultFinancePath } = options;

  if (memory) {
    return createMemoryRouter(routes, {
      initialEntries: [initialPath],
    });
  }

  return createBrowserRouter(routes);
}
```

这段代码要这样讲：

- 独立运行财务子应用时，还是 `createBrowserRouter()`。
- 被 qiankun 嵌入时，外面会传 `memory: true`。
- `initialEntries` 是 memory router 的初始地址，相当于告诉它一开始显示哪个页面。

这一节同样基于最原始的财务路由写法来改。财务子应用内部路由仍然是完整路径，例如：

```js
path: "/finance/bills";
path: "/finance/invoice/908";
path: "/finance/refund/1024";
```

所以传给 `initialEntries` 的也应该继续是完整路径。

### 3.4 第三步：财务子应用挂载时传入 memory 参数

文件位置：`finance-app/src/main.jsx`

修改方式：`局部修改`

原来可能是：

```js
router = createFinanceRouter();
```

改成：

```js
router = createFinanceRouter(
  qiankunWindow.__POWERED_BY_QIANKUN__
    ? {
        memory: true,
        initialPath: window.location.pathname || "/finance/bills",
      }
    : undefined,
);
```

这段代码同样要解释路径转换：

```txt
/finance/bills         -> 账单中心
/finance/invoice/908   -> 开票处理
/finance/refund/1024   -> 退款打款
```

这里建议使用 `qiankunWindow.__POWERED_BY_QIANKUN__`，不要直接用 `window.__POWERED_BY_QIANKUN__`。

原因是：财务子应用是 Vite 子应用，当前项目通过 `vite-plugin-qiankun` 接入 qiankun。这个插件提供了 `qiankunWindow`，它比直接读全局 `window` 更符合 Vite 子应用的接入方式。

这里也先不要把 `/finance` 前缀去掉。因为原始财务子应用的路由表、导航链接、`finance-pages.js` 都是完整路径。等后面单独讲 History + Base/Basename 时，再说明“加了 basename 以后，子应用内部路由才需要改成不带 `/finance` 的路径”。

### 3.5 第四步：重新演示效果

改完以后，重新执行原来的操作：

1. 进入订单子应用。
2. 在订单子应用内部切到订单详情。
3. 切换到财务子应用。
4. 在财务子应用内部切到开票处理或退款打款。
5. 再切回订单子应用。

这时应该观察到：

- 控制台不再出现 `localhost:5173undefined/`。
- 子应用内部页面可以正常切换。
- 但是地址栏不一定跟着子应用内部页面变化。

最后这个现象一定要当场讲出来。

这正是 memory router 的特点：

它把子应用路由从浏览器 history 里隔离出来，所以不再互相覆盖 `history.state`；但也因为它不再写浏览器地址栏，所以会牺牲 URL 同步能力。

这就自然过渡到下一节：为什么还需要“Memory Router + 主应用统一导航”。

## 4. Memory Router 的问题

止血方案能解决报错，但不能把它包装成最终答案。这里要主动讲清楚它的代价。

### 4.1 地址栏不一定跟着子应用内部页面变化

比如用户在财务子应用里从账单中心切到退款打款，页面内容变了，但地址栏可能没有同步变化。

这会带来一个直接问题：用户复制当前地址发给别人，别人打开后不一定能进入同一个子页面。

### 4.2 刷新恢复能力变弱

memory router 的状态保存在内存里。浏览器一刷新，内存状态就没了。

如果地址栏没有记录当前子页面，刷新后就无法准确恢复到刚才那个页面。

### 4.3 浏览器前进后退体验不自然

用户通常期待浏览器后退能够回到上一个子页面。

但是如果子应用内部切换没有写入浏览器 history，浏览器后退可能直接离开当前子应用，或者回到主应用的上一个一级页面。

### 4.4 菜单、权限、埋点会变复杂

企业系统里经常根据 URL 做这些事情：

- 菜单高亮
- 页面权限
- 访问埋点
- 面包屑
- 页签缓存
- 刷新恢复

如果子应用内部路由没有进入地址栏，这些能力就不能只靠 URL 完成，需要额外的主子应用通信协议。

所以这里要给学生一个准确结论：

memory router 不是低级方案，它是隔离方案。它适合某些场景，但如果只使用 memory router 而不做 URL 同步，就会牺牲地址栏、刷新、分享、前进后退这些能力。

## 5. 企业级方案一：Memory Router + 主应用统一导航

这是 memory router 的增强版，也是跨技术栈微前端里很常见的稳妥方案。

核心思想：

子应用嵌入主应用时仍然使用 memory router，但子应用内部点击菜单时，不直接修改浏览器地址，而是通知主应用，由主应用统一修改 URL。

白话解释：

子应用不要自己抢方向盘。子应用告诉主应用“我想去 `/finance/refund/1024`”，真正开车转向的是主应用。

术语解释：

主应用拥有 browser history，子应用通过 qiankun `props` 或统一导航 API 向主应用发起导航请求。主应用完成 `router.push()` 后，再把当前路径同步给子应用的 memory router。

流程可以这样讲：

1. 主应用注册子应用时，通过 `props` 传入导航方法。
2. 子应用嵌入态创建 memory router。
3. 子应用内部点击页面链接时，调用主应用传来的 `navigate(path)`。
4. 主应用执行自己的 `router.push(path)`。
5. 地址栏变成新的 URL。
6. 子应用 memory router 同步到这个路径，渲染对应页面。

这个方案的效果是：

- 子应用不直接覆盖 `window.history.state`。
- 地址栏仍然可以变化。
- 刷新、复制链接、菜单高亮可以继续围绕 URL 设计。
- 主应用可以统一处理权限、埋点、页签、面包屑。

适合场景：

- 多技术栈微前端
- 老项目接入
- 子应用来源复杂
- 主应用需要强管控权限、菜单、页签和埋点
- 平台型中后台系统

代价是：

- 需要设计主子应用之间的导航协议。
- 子应用独立运行和嵌入运行要区分。
- 实现上比单纯 memory router 多一层同步逻辑。

这里要主动回答学生可能冒出的疑问：

“这样是不是让子应用和主应用耦合太多了？”

答案是：确实有耦合，但它不是业务耦合，而是协议耦合。

不好的耦合是子应用直接依赖主应用内部实现，例如直接拿主应用的 Vue Router 实例、主应用 store，或者知道主应用某个组件怎么写。这会让子应用很难独立维护。

可以接受的耦合是主应用提供稳定协议，例如：

```js
navigate(path);
getCurrentPath();
defaultPath;
```

子应用只知道“我要申请跳转”，并不知道主应用底层用的是 Vue Router、React Router，还是别的路由系统。

这和前后端通过 HTTP API 通信很像：前端当然依赖后端接口，但只要接口协议稳定，这种依赖就是可治理的工程边界。

企业里之所以会接受这种方案，是因为很多中后台系统需要主应用统一管理这些能力：

- 菜单高亮
- 页面权限
- 登录失效跳转
- 面包屑
- 页签缓存
- 埋点
- 离开页面确认
- 页面访问审计

如果这些能力都交给每个子应用各自实现，系统越大越难统一。

不过，课堂上的第一版实现可以直接用 qiankun `props`，让学生看清楚主子应用之间到底传了什么。真正企业项目里，通常会再包一层适配器或 SDK。

例如子应用业务代码不直接写：

```js
props.navigate("/finance/invoice/908");
```

而是写成：

```js
microRouter.push("/finance/invoice/908");
```

底层再根据运行环境决定：

- 独立运行时，调用子应用自己的 router。
- 嵌入 qiankun 时，调用主应用传来的 `navigate()`。
- 有需要时，同时做权限、埋点、页签同步。

所以这一方案的准确定位是：平台管控型方案。

它不是“最自由”的方案，但它很稳，特别适合多技术栈、老项目接入、主应用要统一治理的大型中后台。

讲完这里，就可以自然过渡到下一种方案：如果项目是新项目，团队能统一技术栈或统一路由规范，不想让子应用通过主应用协议申请每一次内部跳转，那就可以考虑让每个子应用在自己的 URL 命名空间里自治。这就是下面的 History + Base/Basename 方案。

这一方案可以作为本节后续第一种完整实现。

---

## 6. 企业级方案二：所有应用统一使用 History + Base/Basename

这是新项目里非常常见、也很自然的一种 URL 规划方案。

先用一句白话说清楚：

每个子应用都分到一个固定的地址前缀。主应用看到这个前缀，就知道该挂哪个子应用；子应用自己只关心前缀后面的内部路径。

对应到术语里，这个前缀就是子应用的 URL 命名空间。Vue Router 里叫 `base`，React Router 里叫 `basename`。

本节代码放在 `2/` 目录中。为了把问题讲清楚，这里先不直接接入 React 财务子应用，而是先演示：

```txt
main-app   Vue Router + History
order-app  Vue Router + History + Webpack
user-app   Vue Router + History + Webpack
```

也就是说，第一步先让主应用、订单子应用、用户子应用都使用 Vue Router。这样学生能先看到：同一套路由生态下，History + Base 的配置方式长什么样。

### 6.1 先做纯配置版

先看主应用注册。

修改文件：`2/main-app/src/micro-apps.js`

/users/roles

到这里为止，学生看到的是最理想的配置方式：

1. 主应用 `activeRule` 定一级路径。
2. 子应用 `createWebHistory(base)` 使用同一个一级路径。
3. 子应用内部路由只写内部路径。
4. Webpack 开发服务器开启 `historyApiFallback`，刷新子页面不会 404。

### 6.2 纯配置版会出现什么问题

现在不要急着加修复代码。先让学生看到问题。

默认演示步骤：

```txt
1. 打开 /orders/list
2. 点击订单详情，进入 /orders/detail/2048
3. 点击主应用菜单里的用户子应用，进入 /users/list
4. 点击浏览器后退
```

学生通常会预期回到：

```txt
/orders/detail/2048
```

但是纯配置版可能回到：

```txt
/orders/list
```

甚至在某些兜底逻辑下，可能短暂出现主应用不认识的内部路径，例如：

```txt
/detail/2048
```

为什么都是 Vue Router，还会这样？

关键点是：`base` 主要影响浏览器地址栏，不代表 `history.state` 里保存的一定也是完整路径。

订单子应用使用：

```js
createWebHistory("/orders");
```

地址栏显示的是：

```txt
/orders/detail/2048
```

但是订单子应用自己的 Vue Router 更关心内部路径，所以它写入 `window.history.state.current` 的可能是：

```txt
/detail/2048
```

这对订单子应用自己来说是合理的，因为它的 base 已经是 `/orders`。

但是主应用没有配置 `/orders` base。主应用看到 `/detail/2048` 时，会认为这是一个自己不认识的路径。于是主应用的兜底路由可能把它重定向回：

```txt
/orders/list
```

所以这里要提醒学生：

History + Base/Basename 解决的是 URL 路径边界问题，不等于自动统一了所有应用对 `window.history.state` 的理解。

即使都是 Vue Router，只要主应用和子应用都在同一个浏览器页面里监听 history，也要注意：

```txt
地址栏路径：/orders/detail/2048
子应用内部路径：/detail/2048
主应用识别路径：/orders/detail/2048
```

这三者不是同一个视角。

### 6.3 打开主应用侧的小兜底

修复思路不是让每个子应用都去改自己的路由状态。

更好的边界是：

```txt
子应用：只管 base + 内部路由
主应用：只在跨应用导航边界做一次路径整理
```

当前代码里已经把这段兜底修复先注释起来了。

修改文件：`2/main-app/src/App.vue`

先找到这段注释：

```js
// [路由处理2:] 兜底修复演示：默认先注释，让学生先看到“只做 History + Base 配置”时的跨应用后退问题。
// 讲解问题原因后，再取消下面这段代码和模板里的 @click，即可修复跨子应用后退时主应用误读内部路径的问题。
// function normalizeCurrentHistoryStateForHost() {
//   ...
// }
```

讲解完问题以后，取消这三个函数的注释：

```js
function normalizeCurrentHistoryStateForHost() {
  const state = window.history.state;
  const browserPath =
    window.location.pathname + window.location.search + window.location.hash;
  const currentBase = getCurrentMicroAppBase(browserPath);

  if (!state || !currentBase) {
    return;
  }

  window.history.replaceState(
    {
      ...state,
      back: normalizeHistoryPath(state.back, currentBase),
      current: browserPath,
      forward: normalizeHistoryPath(state.forward, currentBase),
    },
    "",
    browserPath,
  );
}

function getCurrentMicroAppBase(path) {
  if (path.startsWith("/orders")) {
    return "/orders";
  }

  if (path.startsWith("/users")) {
    return "/users";
  }

  return "";
}

function normalizeHistoryPath(path, currentBase) {
  if (typeof path !== "string") {
    return path;
  }

  if (path.startsWith("/orders") || path.startsWith("/users")) {
    return path;
  }

  return `${currentBase}${path}`;
}
```

再在主应用菜单的 `RouterLink` 上恢复点击事件。

修改文件：`2/main-app/src/App.vue`

```vue
<RouterLink
  v-for="item in menuItems"
  :key="item.name"
  class="menu-button"
  :class="{ active: currentApp.name === item.name }"
  :to="item.defaultPath"
  @click="normalizeCurrentHistoryStateForHost"
>
  <strong>{{ item.label }}</strong>
</RouterLink>
```

这段兜底做了什么？

它只在用户点击主应用菜单、准备跨子应用切换之前执行一次。

例如当前在订单详情页：

```txt
浏览器地址：/orders/detail/2048
订单子应用内部 current：/detail/2048
```

点击用户子应用之前，主应用把当前这条历史记录整理成：

```js
{
  back: "/orders/list",
  current: "/orders/detail/2048",
  forward: null
}
```

然后再进入：

```txt
/users/list
```

这样浏览器后退时，主应用能读懂上一条记录是订单详情，而不是一个孤零零的 `/detail/2048`。

注意这个兜底的边界：

- 不放在订单子应用里。
- 不放在用户子应用里。
- 只放在主应用跨子应用导航的位置。
- 子应用内部跳转仍然保留自己的内部路径。

这就是平台侧治理，而不是业务子应用互相耦合。

#### 6.4.3 复现 React 接入后的问题

启动四个应用：

```bash
pnpm --dir ./2 dev:with-finance
```

然后按这个顺序操作：

```txt
1. 打开 http://localhost:5173
2. 进入订单子应用：/orders/list
3. 点击订单详情：/orders/detail/2048
4. 点击财务子应用：/finance/bills
5. 在财务子应用内部点击开票处理：/finance/invoice/908
6. 再点击主应用左侧的订单子应用
```

此时可能会看到类似错误：

```txt
[Vue Router warn]: Error with push/replace State SecurityError:
Failed to execute 'replaceState' on 'History':
A history state object with URL 'http://localhost:5173undefined/' cannot be created
in a document with origin 'http://localhost:5173'
and URL 'http://localhost:5173/finance/invoice/908'.
```

这段错误要先用白话讲：

主应用准备从财务页面切回订单页面时，Vue Router 想更新浏览器历史记录。但它从 `history.state` 里读到的数据已经不是 Vue Router 熟悉的格式，于是内部拼出了一个带 `undefined` 的地址，浏览器发现这个地址不合法，就拒绝执行。

再说术语：

这是 Vue Router 和 React Router 共享同一个 `window.history` 时产生的 `history.state` 结构冲突。

#### 6.4.4 错误原因：basename 不负责统一 history.state

这里是本节最关键的地方。

`basename` 只告诉 React Router：

```txt
你的页面挂在 /finance 下面。
```

它解决的是 URL 命名空间问题。

但是 `basename` 不会告诉 React Router：

```txt
你写 history.state 时，还要保留 Vue Router 需要的字段。
```

Vue Router 常见的 `history.state` 结构类似：

```js
{
  back: "/orders/list",
  current: "/orders/detail/2048",
  forward: null,
  position: 2,
  replaced: false,
  scroll: null
}
```

这些字段是 Vue Router 用来判断当前页面、上一页、下一页、历史栈位置和滚动恢复的。

React Router 常见的 `history.state` 结构类似：

```js
{
  usr: null,
  key: "oaurn36m",
  idx: 1
}
```

这些字段是 React Router 自己用来维护导航状态的。

所以问题不是 React Router 写错了，也不是 Vue Router 写错了。它们各自在独立应用里都是合理的。

真正的问题是：

```txt
微前端嵌入后，主应用 Vue Router 和财务子应用 React Router 共享同一个浏览器 history。
```

财务子应用内部从 `/finance/bills` 跳到 `/finance/invoice/908` 时，React Router 会写入自己的 state。主应用后面再执行跳转时，Vue Router 仍然按自己的字段约定去读 state，读不到 `current`、`position` 这些字段，就可能出现 `undefined/`。

这里一定要提醒学生：

```txt
同样使用 History + Base/Basename，不代表所有路由库对 history.state 的结构约定一致。
```

History + Base/Basename 解决的是“地址归谁管”的第一层问题；混合路由库时，还要解决“history.state 怎么兼容”的第二层问题。

#### 6.4.5 解决思路：让 React Router 写 state 时保留 Vue Router 字段

这一节的修复思路不是让主应用去猜 React Router 的每一种内部状态，也不是让 Vue Router 放弃自己的字段。

更合适的边界是：

```txt
React 财务子应用在写 history.state 时，保留已有字段，再合并自己的字段。
```

也就是说，React Router 仍然可以写它需要的：

```js
usr;
key;
idx;
```

但同时不要把 Vue Router 需要的这些字段清掉：

```js
back;
current;
forward;
position;
replaced;
scroll;
```

当前代码已经准备好了这个兼容层。

修改文件：`2/finance-app/src/router.jsx`

先看第一个方法：

```js
function createStatePreservingWindow() {
  if (!qiankunWindow.__POWERED_BY_QIANKUN__) {
    return window;
  }

  const browserHistory = window.history;

  const historyProxy = {
    get length() {
      return browserHistory.length;
    },
    get state() {
      return browserHistory.state;
    },
    go: browserHistory.go.bind(browserHistory),
    back: browserHistory.back.bind(browserHistory),
    forward: browserHistory.forward.bind(browserHistory),
    pushState(state, title, url) {
      browserHistory.pushState(
        createMergedHistoryState(state, url, false),
        title,
        url,
      );
    },
    replaceState(state, title, url) {
      browserHistory.replaceState(
        createMergedHistoryState(state, url, true),
        title,
        url,
      );
    },
  };

  return new Proxy(window, {
    get(target, prop) {
      if (prop === "history") {
        return historyProxy;
      }
      const value = target[prop];
      return typeof value === "function" ? value.bind(target) : value;
    },
  });
}
```

这段代码的作用：

给 React Router 一个代理版的 `window`。React Router 以为自己还是在调用 `window.history.pushState()` 和 `window.history.replaceState()`，但实际上这两个方法已经被我们拦截了。

拦截以后，每次写入 state 之前，都会先调用：

```js
createMergedHistoryState(state, url, replaced);
```

再看第二个方法：

```js
function createMergedHistoryState(state, url, replaced) {
  const currentState = window.history.state ?? {};
  const targetUrl = new URL(url || window.location.href, window.location.href);
  const currentPath = targetUrl.pathname + targetUrl.search + targetUrl.hash;
  const previousPath =
    typeof currentState.current === "string"
      ? currentState.current
      : window.location.pathname +
        window.location.search +
        window.location.hash;
  const previousPosition =
    typeof currentState.position === "number"
      ? currentState.position
      : window.history.length - 1;

  return {
    ...currentState,
    ...state,
    back: replaced ? (currentState.back ?? null) : previousPath,
    current: currentPath,
    forward: null,
    replaced,
    position: replaced ? previousPosition : previousPosition + 1,
    scroll: currentState.scroll ?? null,
  };
}
```

这段代码的作用：

先保留当前 `history.state` 里已有的字段，再合并 React Router 传进来的字段，最后补齐 Vue Router 需要的 `back/current/position` 等字段。

修复以后，财务内部页的 state 会从这种 React Router 单独结构：

```js
{
  usr: null,
  key: "xxx",
  idx: 1
}
```

变成兼容结构：

```js
{
  back: "/finance/bills",
  current: "/finance/invoice/908",
  forward: null,
  replaced: false,
  position: 7,
  scroll: null,
  usr: null,
  key: "xxx",
  idx: 1
}
```

这样 React Router 能继续读自己的 `usr/key/idx`，主应用 Vue Router 后续也能读到自己需要的 `back/current/position`。

#### 6.4.7 这一段最后怎么总结

这一小节不要总结成“React 子应用必须这么写”。更准确的结论是：

1. History + Base/Basename 是 URL 命名空间方案。
2. 它能清楚划分 `/orders/*`、`/users/*`、`/finance/*` 分别归谁。
3. 但是它不自动统一不同路由库写入 `history.state` 的结构。
4. Vue Router + React Router 混用时，如果都直接操作浏览器 history，就要处理 state 兼容问题。
5. 当前演示用 `createStatePreservingWindow()` 让 React Router 写 state 时保留 Vue Router 需要的字段。
6. 如果团队不想维护这些兼容逻辑，方案一的 Memory Router + 主应用统一导航通常更稳。

## 7. 其他方案只讲思路



> 我们把握住重点，qiankun 路由治理不是在选 hash、history、memory，而是在分配路由主权：要么由主应用统一掌控浏览器 URL 和路由状态，走统一导航。
>
> 要么按 URL 命名空间把控制权分给各个子应用，走命名空间自治；
>
> 就算有其他方案，本质上都是在这两个方向之间做取舍、弱化或封装。

### 7.1 Hash 隔离

先用白话解释：

主应用继续使用正常路径，子应用把自己的内部路径放到 `#` 后面。这样主应用主要看 `#` 前面的路径，子应用主要看 `#` 后面的路径。

例如：

```txt
/finance/#/refund/1024
```

这里可以拆开看：

```txt
/finance        主应用用它判断要挂载财务子应用
#/refund/1024   财务子应用用它判断内部页面
```

这个方案的核心逻辑是：

```txt
主应用和子应用不要都争同一段 pathname。
```

也就是说，主应用负责 `location.pathname`，子应用负责 `location.hash`。

这个方案能解决什么？

- 子应用路由和主应用 path 有一定隔离。
- 老项目迁移成本低。
- 服务端 history fallback 压力小。

尤其是老系统里，很多子应用本来就是 hash 路由。迁移到 qiankun 时，不需要一上来把所有内部路由改成 history 模式，成本会低很多。

但是它也有明显代价：

- URL 不够统一。
- 主应用如果要做菜单、权限、埋点，需要同时解析 path 和 hash。
- 浏览器地址会变成 `/finance/#/refund/1024` 这种形态，不如 `/finance/refund/1024` 清爽。
- Hash Router 仍然可能调用 `history.pushState()` 或 `history.replaceState()`，所以它不是绝对的 `history.state` 隔离方案。



### 7.2 子应用完全自治

先用白话解释：

主应用只负责把子应用挂出来，进入子应用以后，子应用内部怎么跳、怎么保存路由、怎么恢复页面，都由子应用自己管。

比如主应用只关心这几个入口：

```txt
/orders   订单系统
/finance  财务系统
/users    用户系统
```

但是进入 `/finance` 以后，财务内部的这些页面：

```txt
/finance/bills
/finance/invoice/908
/finance/refund/1024
```

都由财务子应用自己维护。主应用不关心哪个是账单、哪个是开票、哪个是退款。

这个方案的核心逻辑是：

```txt
主应用只管入口，不管子应用内部页面。
```

主应用只需要保证：只要地址还在 [/finance/*](vscode-file://vscode-app/Applications/Visual Studio Code.app/Contents/Resources/app/out/vs/code/electron-browser/workbench/workbench.html) 下面，就继续挂载财务子应用。

也就是说，主应用不会关心你是账单页、开票页还是退款页。它只判断：

**问题出在哪里？**

如果主应用还想统一控制这些能力：

那子应用完全自治就会很难受。因为主应用不知道子应用内部到底发生了什么，它只能看到 URL 变化，或者通过额外协议等子应用上报。

所以这套方案更适合**“门户型系统”**。

比如主应用只是一个统一入口：

进入财务以后，财务系统内部像一个独立应用：

这种情况下，主应用不需要强控制浏览器行为。它只负责保证 [/finance/*](vscode-file://vscode-app/Applications/Visual Studio Code.app/Contents/Resources/app/out/vs/code/electron-browser/workbench/workbench.html) 始终能挂上财务子应用即可。

但如果你做的是平台型中后台，主应用要统一控制所有子应用的菜单、权限、页签、面包屑和访问轨迹，那“子应用完全自治”就不太适合。因为它会把路由控制权分散到每个子应用里，平台层很难统一治理。

所以它的本质是：

```
控制权下放，平台管控变弱，子应用自由度变高。
```

这就是它的取舍。

### 7.3 统一微前端路由服务

先用白话解释：

不要让每个应用直接操作浏览器路由，而是在主应用和子应用之间放一层统一的路由服务。所有应用想跳转时，都调用这层服务。

也就是说，子应用不直接写：

```js
router.push("/finance/refund/1024");
```

而是写：

```js
microAppRouter.push("/finance/refund/1024");
```

这个方案的核心逻辑是：

```txt
不要把路由治理散落在每个子应用里，而是收敛到一个统一入口。
```

前面讲的“Memory Router + 主应用统一导航”，其实就是统一路由服务的一种教学版实现。区别是：课堂里我们直接通过 qiankun props 传 `navigate`，让学生看清楚主子应用怎么通信；企业项目里通常会再包成一个 SDK。



**这个方案能解决什么？**

- 路由入口统一。
- 主应用可以统一做权限、菜单、页签和埋点。
- 子应用不用知道主应用底层是 Vue Router 还是 React Router。
- 子应用独立运行和嵌入运行可以共用一套业务跳转代码。

**它的代价是：**

- 前期要设计一套稳定 API。
- 子应用要改造跳转入口，不能到处直接调用自己的 router。
- 平台层一旦设计不好，会变成新的强耦合点。

所以这套方案适合大型平台，但不适合课程一开始就完整铺开。

课堂里可以这样总结：

统一微前端路由服务不是另一种孤立技巧，而是把“谁负责跳转、谁负责记录、谁负责权限和埋点”收敛成平台协议。

项目越大，这种收敛越有价值；项目越小，直接使用 qiankun props 或 History + Base/Basename 可能就够了。

## 8. 本节最终选择哪两种方案展示

本节后续展示两种方案，但展示深度不同。

### 8.1 第一种：Memory Router + 主应用统一导航

这套方案用来说明：

跨技术栈、老项目接入、子应用复杂时，企业项目经常会选择让主应用统一拥有浏览器 URL。

展示效果：

1. 子应用嵌入态不再直接改 `window.history.state`。
2. 控制台不再出现 `replaceState` 报错。
3. 子应用内部点击页面时，地址栏仍然可以变化。
4. 主应用可以统一管理菜单、权限、埋点和页签。

课堂结论：

memory router 不是终点，memory router + 主应用导航协议才是更完整的企业级方案。

### 8.2 第二种：所有应用统一 History + Base/Basename

这套方案用来说明：

如果是新项目，且团队能从一开始统一 URL 规划，同时路由生态一致或有统一路由封装，那么所有应用统一使用 history，并严格配置 base/basename，通常是成本较低、体验自然的方案。

展示效果：

1. 子应用内部切路由时，地址栏天然变化。
2. 刷新后能根据 URL 回到对应子页面。
3. 复制链接可以直接访问对应页面。
4. 后续做“路由保持”和 KeepAlive 更容易讲清楚。

课堂结论：

History + Base/Basename 不是“所有项目都无脑使用”的答案。它适合新项目、URL 规范统一、同路由生态或有统一路由封装的团队。

在当前 Vue Router + React Router 混合技术栈 demo 里，这个方案只作为对比讲解，不作为最终稳定实现。







## 9. 为后续课程埋伏笔：路由保持和 KeepAlive

后续课程可以继续讲路由保持，但要先区分两件事：

- URL 仍然应该表达当前子页面位置。
- 谁来写这个 URL，要看采用哪种路由 ownership 方案。

如果是同路由生态的新项目，可以基于 History + Base/Basename 讲路由保持。

如果是当前这种 Vue Router + React Router 混合技术栈，更稳的是基于“Memory Router + 主应用统一导航”讲路由保持：子应用发起导航请求，主应用更新 URL，子应用 memory router 同步到对应页面。

路由保持解决的是：

用户切到某个子应用内部页面后，再切到另一个子应用，之后切回来，应该回到刚才那个子页面。

例如：

```txt
/orders/detail/2048
```

切到财务：

```txt
/finance/refund/1024
```

再切回订单时，不回默认的：

```txt
/orders/list
```

而是回到上一次访问过的：

```txt
/orders/detail/2048
```

这里可以告诉学生：

路由保持保存的是“地址”。KeepAlive 保存的是“组件实例状态”。

两者不是一回事。

例如：

- 路由保持：回来后仍然是 `/orders/detail/2048`。
- KeepAlive：回来后页面里的表单输入、滚动位置、组件内部状态还在。

这也是为什么后续课程仍然要围绕 URL 讲：URL 本身应该表达当前子页面位置，学生更容易理解“恢复地址”和“保留组件状态”的区别。

只是当前混合技术栈项目里，URL 最好由主应用统一写，而不是让 Vue Router 和 React Router 同时直接拥有 browser history。

## 10. 本节授课总结

最后可以这样收束：

微前端里的路由问题，不是简单问“用 hash 还是 history”，而是要先判断谁拥有浏览器地址栏。

如果多个应用同时直接操作 `window.history`，就可能出现路由状态互相覆盖。

Memory Router 可以隔离冲突，但如果不做 URL 同步，会牺牲刷新、分享、前进后退等能力。

Memory Router + 主应用统一导航适合跨技术栈、老项目接入、主应用强管控的企业系统。

History + Base/Basename 适合新项目、统一 URL 规划、团队规范清晰，并且同路由生态或有统一路由封装的系统。

所以企业级方案不是只有一种。真正重要的是根据项目条件选择合适的路由 ownership：

- 谁负责改地址栏？
- 谁负责保存当前路径？
- 谁负责恢复子应用页面？
- 谁负责权限、菜单、埋点和页签？

把这些边界讲清楚，学生才真正理解微前端路由处理，而不是只记住几个 API 名字。
