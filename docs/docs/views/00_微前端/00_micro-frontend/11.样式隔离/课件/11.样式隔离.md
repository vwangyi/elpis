# 11. qiankun 的样式隔离

## 这节课要拿到什么结果

这一课只解决一个问题：子应用的 CSS 被加载到主应用页面以后，为什么可能影响主应用和其他子应用，qiankun 又能做哪些处理。

先记住一句话：

```txt
DOM 有容器边界，不代表普通 CSS 自动有应用边界。
```

这一课你要拿到 4 个结论：

- 普通 CSS 进入同一个 `document` 后，会按选择器匹配整个页面
- qiankun 默认管理的是样式生命周期，不是 CSS 作用域
- `experimentalStyleIsolation` 的本质是运行时选择器改写
- `strictStyleIsolation` 的本质是 Shadow DOM 隔离，隔离更强，但适配成本也更高

上一课讲的是 JS 沙箱。JS 沙箱重点管的是 `window` 这类运行时全局对象；这一课讲的是 CSS 选择器能影响哪些元素。它们都叫“隔离”，但不是同一套机制。

本节配套代码在本课示例目录中。

```txt
样式污染-演示.html：普通 CSS 为什么会污染整个页面。
选择器改写隔离-演示.html：选择器改写型隔离的最小模型。
ShadowDOM隔离-演示.html：Shadow DOM 严格隔离的最小模型。
main-app、order-app、finance-app：qiankun 项目里的样式加载、卸载、保活和隔离配置演示。
```

## 1. CSS 为什么会污染

先说白话：

CSS 是按选择器找元素的。普通 CSS 进入页面以后，默认面对的是整个页面，不是某一个微前端应用。

比如订单子应用写了：

```css
.card {
  padding: 24px;
}

button {
  color: red;
}
```

浏览器不会问：

```txt
这个 .card 是不是订单应用里的？
这个 button 是不是订单应用里的？
```

浏览器只会问：

```txt
当前 document 里有没有 .card？
当前 document 里有没有 button？
```

只要匹配上，样式就会生效。

术语说：

```txt
普通 CSS 规则会参与当前 document 的全局样式计算。
除非使用选择器约束、Shadow DOM、iframe 或构建期作用域方案，否则 CSS 本身不知道应用边界。
```

打开文件：`样式污染-演示.html`

这个页面里有三个区域：

- 主应用
- 订单子应用
- 财务子应用

它们都有同样的类名：

```html
<div class="card">
  <button class="action-button">按钮</button>
</div>
```

然后页面模拟订单应用加载了这段 CSS：

```css
.card {
  border-color: #dc2626;
  background: #fff1f2;
}

.action-button {
  background: #dc2626;
}
```

如果这段 CSS 直接插进页面，它影响的不是订单应用自己的 `.card`，而是页面里所有 `.card`。

所以这里先把根因说清楚：

```txt
子应用挂在自己的 DOM 容器里，不等于子应用 CSS 自动只影响这个容器。
```

## 2. qiankun 是怎么把子应用样式带进页面的

讲样式隔离前，要先知道样式是怎么进入主应用页面的。

qiankun 接入子应用时，不是把子应用放进 iframe。它走的是 HTML Entry。

白话说：

```txt
主应用拿到子应用入口 HTML。
qiankun 把里面的 JS 和 CSS 资源解析出来。
JS 会被包装执行。
CSS 会被拉取、内联，再跟着子应用 DOM 一起插入主应用页面。
```

过程可以简化成：

```txt
1. 主应用注册子应用 entry。
2. qiankun 根据 activeRule 或 loadMicroApp 判断子应用是否应该加载。
3. import-html-entry 请求子应用 HTML。
4. import-html-entry 解析 HTML 里的 link、style、script。
5. 外链 CSS 会被 fetch 成 CSS 文本。
6. 原来的 link 位置会被替换成 style。
7. qiankun 拿到处理后的子应用 HTML 字符串。
8. qiankun 把 HTML 字符串变成 wrapper DOM。
9. wrapper DOM 被插入主应用配置的 container。
10. wrapper 里的 style 开始在当前 document 生效。
```

所以重点不是“样式被谁加载了”，而是：

```txt
子应用样式最终仍然在主应用当前 document 里参与匹配。
```

只要它进入同一个 `document`，普通选择器就有机会命中别的应用。

## 3. 默认样式管理到底是什么意思

很多资料会说 qiankun 默认能处理样式问题。这里要分清楚：

```txt
默认样式管理，不等于真正隔离 CSS 作用范围。
```

先说白话：

```txt
子应用加载时，qiankun 把它的样式带进页面。
子应用卸载时，qiankun 尽量让这些样式不再继续影响页面。
```

也可以记成：

```txt
默认能力更像“样式跟着应用来，也跟着应用走”。
```

这里的“生命周期”指的是子应用的加载、挂载、卸载。

比如财务应用被激活：

```txt
/finance 命中 activeRule
  ↓
qiankun 加载 finance-app
  ↓
finance-app 的 CSS 被插进页面
  ↓
财务页面样式生效
```

离开财务应用：

```txt
当前地址不再命中 /finance
  ↓
qiankun unmount finance-app
  ↓
财务应用 wrapper 被移走
  ↓
wrapper 里的 style 也不再生效
```

所以默认样式管理能做到：

```txt
1. 子应用挂载时让样式进入页面。
2. 子应用卸载时让这批样式随 wrapper 失效或移除。
3. 对部分动态插入的 style/link 做记录、清理和重建。
4. 减少单实例切换时上一个子应用样式长期残留到下一个子应用。
```

但它不能做到：

```txt
1. 不能保证子应用样式只影响自己的容器。
2. 不能保证主应用样式不影响子应用。
3. 不能保证多个同时挂载的子应用之间不互相影响。
4. 不能彻底处理 body、html、:root 这类全局选择器。
5. 不能彻底处理 @keyframes、@font-face、@import、@page 等规则。
6. 不能自动处理组件库弹窗、下拉框挂到 document.body 以后带来的边界问题。
```

这一节最容易记错的地方就在这里：

```txt
qiankun 默认管的是样式生命周期，不是样式作用域。
```

## 4. 项目里观察默认样式生命周期

文件位置：`main-app/src/micro-apps.js`

修改方式：`查看现有文件`

本节项目里有两个子应用，刚好可以观察两种生命周期。

```js
const microApps = {
  order: {
    name: "order-app",
    entry: "//localhost:5174",
    activeRule: "/orders",
  },
  finance: {
    name: "finance-app",
    entry: "//localhost:5175",
    activeRule: "/finance",
  },
};
```

财务应用通过 `registerMicroApps` 注册：

```js
registerMicroApps([
  {
    name: microApps.finance.name,
    entry: microApps.finance.entry,
    container: "#normal-subapp-viewport",
    activeRule: microApps.finance.activeRule,
    props: createRouteProps(router, microApps.finance),
  },
]);
```

它的特点是：

```txt
进入 /finance 时，qiankun 挂载财务应用。
离开 /finance 时，qiankun 卸载财务应用。
```

订单应用通过 `loadMicroApp` 手动加载：

```js
orderMicroApp = loadMicroApp(
  {
    name: microApps.order.name,
    entry: microApps.order.entry,
    container: "#order-viewport",
    props: createOrderProps(router, true),
  },
  qiankunSandboxOptions,
);
```

切走订单应用时，主应用没有调用 `unmount()`：

```js
function hideOrderMicroApp(router) {
  orderMicroApp?.update?.(createOrderProps(router, false));
}
```

它的特点是：

```txt
订单应用第一次进入时加载。
切到财务时只是隐藏和 update，不销毁实例。
订单 DOM、状态和样式都还在。
```

这两个应用放在一起，就能看到一个关键判断：

```txt
样式生命周期跟应用生命周期绑定。
应用 unmount，样式才有机会跟着走。
应用 keep alive，样式也会继续留在页面里。
```

## 5. 财务应用：样式随挂载和卸载变化

文件位置：`finance-app/src/views/BillsView.jsx`

修改方式：`查看现有文件`

财务页面里有一张专门观察生命周期的卡片：

```jsx
<article className="view-card finance-lifecycle-card lifecycle-style-marker">
  <h2>本月账单概览</h2>
  <p>回款进度 76%，本月异常账单 5 笔。</p>
</article>
```

对应样式在这个文件里：

文件位置：`finance-app/src/style.css`

修改方式：`查看现有文件`

```css
.finance-lifecycle-card.lifecycle-style-marker {
  border: 4px solid #c2410c;
  border-left-width: 14px;
  background:
    linear-gradient(135deg, rgba(194, 65, 12, 0.16), transparent 48%), #fff7ed;
  box-shadow: 0 20px 42px rgba(194, 65, 12, 0.24);
}
```

运行时观察：

```txt
1. 打开主应用 http://localhost:5173/orders/list。
2. 打开控制台，执行 document.querySelector('.lifecycle-style-marker')，结果应该是 null。
3. 切到 /finance/bills。
4. 财务页面出现带橙色边框的卡片。
5. 再执行 document.querySelector('.lifecycle-style-marker')，能找到财务卡片 DOM。
6. 再切回 /orders/list。
7. 再执行 document.querySelector('.lifecycle-style-marker')，结果应该重新变成 null。
```

这里观察的是：

```txt
财务应用 DOM 随 mount 出现，随 unmount 消失。
```

它不是因为 CSS 被隔离了，而是因为财务应用 wrapper 离开了页面。

注意，不建议直接在 Elements 面板全文搜索 `lifecycle-style-marker` 来判断。因为 Vite 开发模式可能把 CSS 文本留在 `<style>` 标签里，全文搜索可能搜到样式文本，不代表财务 DOM 还在。

更稳的判断方式是：

```js
document.querySelector(".lifecycle-style-marker");
```

这个查的是 DOM 元素是否还在页面里。

## 6. 订单应用：保活后样式不会自然退出

文件位置：`order-app/src/views/OrderListView.vue`

修改方式：`查看现有文件`

订单页面里有一张保活观察卡片：

```vue
<article class="view-card view-card-strong keep-alive-style-marker notice-card">
  <h2>今日订单概览</h2>
  <p>履约完成率 92%，当前保留草稿 3 份。</p>
</article>
```

对应样式在这个文件里：

文件位置：`order-app/src/style.css`

修改方式：`查看现有文件`

```css
.keep-alive-style-marker {
  border: 4px solid #0f766e;
  border-left-width: 14px;
  background:
    linear-gradient(135deg, rgba(15, 118, 110, 0.18), transparent 48%), #ecfdf5;
  box-shadow: 0 20px 42px rgba(15, 118, 110, 0.26);
}
```

运行时观察：

```txt
1. 进入 /orders/list。
2. 订单页面出现带绿色粗边框和左侧色条的卡片。
3. 切到 /finance/bills。
4. 订单应用容器被隐藏，但订单实例没有 unmount。
5. 打开控制台，执行 document.querySelector('#order-viewport .keep-alive-style-marker')，仍然能找到订单卡片 DOM。
6. 观察财务页面的 notice-card，可能会被订单应用样式染成绿色效果。
7. 再切回 /orders/list，订单页面和状态直接恢复。
```

为什么财务卡片可能会变绿？看订单应用里这段样式：

```css
.module-content .notice-card {
  transform: translateY(-8px);
  border-color: #047857;
  outline: 12px solid rgba(5, 150, 105, 0.32);
  background:
    linear-gradient(135deg, rgba(5, 150, 105, 0.34), transparent 42%),
    linear-gradient(180deg, #d1fae5 0%, #ecfdf5 100%);
  box-shadow: 0 28px 56px rgba(4, 120, 87, 0.36);
}
```

这不是推荐写法，而是演示材料。

它故意使用了比较宽的选择器 `.module-content .notice-card`。财务应用里也有 `notice-card`，所以当订单应用保活、订单样式还在当前 `document` 里时，这条规则就有机会命中财务卡片。

这里要分开看两件事：

```txt
订单 DOM 仍然存在：因为订单应用被 keep alive，没有 unmount。
订单 CSS 仍然参与匹配：因为它还在当前 document 里。
```

所以 keep alive 场景更需要谨慎处理样式边界。

## 7. experimentalStyleIsolation：选择器改写型隔离

默认样式管理管的是生命周期。如果要限制 CSS 作用范围，就需要额外方案。

qiankun 提供的第一个方案是：

```js
start({
  sandbox: {
    experimentalStyleIsolation: true,
  },
});
```

白话说：

```txt
qiankun 给子应用容器加一个特殊标记。
然后把子应用 CSS 选择器改写成“必须在这个容器下面才生效”。
```

比如子应用原来写：

```css
.app-main {
  font-size: 14px;
}
```

qiankun 会改成类似：

```css
div[data-qiankun-react16] .app-main {
  font-size: 14px;
}
```

这就是选择器改写。

打开文件：`选择器改写隔离-演示.html`

这个 demo 做了三件事：

```txt
1. 页面里有主应用、订单子应用、财务子应用三个区域。
2. 先加载未改写 CSS，三个区域都会被影响。
3. 再加载改写后 CSS，只有 data-qiankun-order 下面的订单区域会被影响。
```

里面有一个教学用的最小改写函数：

```js
function scopeCss(cssText, scopeSelector) {
  return cssText.replace(
    /(^|})\s*([^@{}][^{}]*)\s*{/g,
    (match, close, selectorText) => {
      const scopedSelector = selectorText
        .split(",")
        .map((selector) => `${scopeSelector} ${selector.trim()}`)
        .join(", ");

      return `${close}\n${scopedSelector} {`;
    },
  );
}
```

这段不是 qiankun 源码，只是把选择器改写动作缩到最小。

它做的事可以理解成：

```txt
普通选择器：.card
改写以后：[data-qiankun-order] .card
```

这样浏览器匹配 `.card` 时，会多一个前提：

```txt
这个 .card 必须在 [data-qiankun-order] 容器里面。
```

真实 qiankun 不只是靠一条正则硬切 CSS 文本。它会找到 style 标签，读取浏览器解析后的 CSS 规则，再对普通规则做 scoped CSS 处理。

但它也不是万能的。官方文档提醒过，下面这些规则不支持或不适合用这种方式处理：

```txt
@keyframes
@font-face
@import
@page
```

原因很简单：它们不是普通选择器，不能直接在前面加一个容器前缀。

所以准确说法是：

```txt
experimentalStyleIsolation 是运行时 scoped css。
它能降低普通 class、标签选择器、后代选择器造成的冲突，但不是强隔离。
```

## 8. strictStyleIsolation：Shadow DOM 严格隔离

qiankun 还提供了另一个配置：

```js
start({
  sandbox: {
    strictStyleIsolation: true,
  },
});
```

这个配置背后用的是 Shadow DOM。

先用白话说：

```txt
Shadow DOM 可以理解成浏览器给某个 DOM 节点挂了一棵相对独立的小 DOM 树。
这棵树还在同一个页面里，不是 iframe。
但它有一层浏览器提供的边界，普通外部 CSS 不会随便穿进去，里面的 CSS 也不会随便影响外面。
```

术语说：

```txt
Shadow DOM 是 Web Components 体系中的一部分，用来提供 DOM 封装和样式边界。
```

这一课只需要记三个词：

```txt
shadow host：挂载 Shadow DOM 的外层节点。
shadow root：调用 attachShadow 后创建出来的根。
shadow tree：shadowRoot 里面那棵 DOM 树。
```

最小代码是：

```js
const host = document.querySelector("#order-app");
const shadowRoot = host.attachShadow({ mode: "open" });

shadowRoot.innerHTML = `
  <style>
    button {
      color: red;
    }
  </style>

  <button>订单按钮</button>
`;
```

这段代码的意思是：

```txt
#order-app 是 shadow host。
attachShadow 创建 shadowRoot。
style 和 button 被放进 shadowRoot。
style 里的 button 通常只影响 shadowRoot 里的 button。
```

打开文件：`ShadowDOM隔离-演示.html`

这个 demo 只观察一件事：

```txt
右侧 Shadow DOM 里的 button 被改成红色，左侧主应用普通 DOM 的 button 不受影响。
```

开启 `strictStyleIsolation` 后，qiankun 可以简化理解成做了这几步：

```txt
1. 创建子应用 wrapper。
2. 给 wrapper attachShadow。
3. 把子应用内容放进 shadowRoot。
4. 后续渲染时返回 shadowRoot 作为子应用容器。
```

它的优点是：

```txt
浏览器原生隔离更强。
子应用内部普通样式不容易污染外部页面。
外部普通样式也不容易影响子应用内部。
```

但它不是无脑开启。

常见适配问题包括：

```txt
1. 组件库弹窗、下拉框、Tooltip 默认挂到 document.body，会跑出 shadowRoot。
2. 全局 reset、主题变量、字体样式可能进不去 shadowRoot。
3. 有些第三方库默认用 document.querySelector 查找节点，可能查不到 shadowRoot 内部。
4. 主应用想覆盖子应用样式会变难。
5. 部分框架或组件库需要额外配置弹层容器。
```

所以工程判断是：

```txt
strictStyleIsolation 隔离更强，但适配成本也更高。
```

## 9. 项目里怎么切换 qiankun 样式隔离配置

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

本节项目把三个配置写在同一个位置，课堂上每次只打开一个。

默认演示配置是：

```js
const qiankunSandboxOptions = {
  sandbox: true,
  // sandbox: {
  //   experimentalStyleIsolation: true,
  // },
  // sandbox: {
  //   strictStyleIsolation: true,
  // },
};
```

它用于观察：

```txt
默认沙箱开启时，样式会随子应用生命周期进入和退出。
但 CSS 作用范围没有被真正限制。
```

如果要演示选择器改写，把它改成：

```js
const qiankunSandboxOptions = {
  sandbox: {
    experimentalStyleIsolation: true,
  },
};
```

观察重点：

```txt
1. 子应用 wrapper 上出现 data-qiankun-xxx 标记。
2. 子应用 style 里的普通选择器被加上作用域前缀。
3. 普通 class 冲突明显减少。
4. 财务页面的 notice-card 不应该再被订单应用样式命中。
```

如果要演示 Shadow DOM，把它改成：

```js
const qiankunSandboxOptions = {
  sandbox: {
    strictStyleIsolation: true,
  },
};
```

观察重点：

```txt
1. 子应用 wrapper 下面出现 shadowRoot。
2. 子应用 DOM 和 style 进入 shadowRoot。
3. 内外普通样式隔离更明显。
4. 同时观察组件、弹层、全局样式是否有适配问题。
```

课堂上不要把三个配置同时打开。建议顺序是：

```txt
先 sandbox: true。
再 experimentalStyleIsolation: true。
最后 strictStyleIsolation: true。
```

每次只改一个变量，观察结果会清楚很多。

## 10. 工程上还要做什么

qiankun 的样式隔离能力很重要，但真实项目不能只靠一个配置。

更稳的组合通常是：

```txt
1. 主应用和子应用约定 class 命名前缀。
2. 组件库配置 prefix class，也就是类名前缀，避免组件库类名冲突。
3. 子应用内部使用 CSS Modules、Scoped CSS、CSS-in-JS 等构建期作用域方案。
4. 需要运行时兜底时，再考虑 experimentalStyleIsolation。
5. 需要更强隔离时，再评估 strictStyleIsolation 和 Shadow DOM 适配成本。
```

为什么不建议所有问题都丢给 qiankun？

因为 CSS 有很多全局能力：

```txt
body
html
:root
@font-face
@keyframes
组件库 portal
动态 style
第三方脚本注入样式
```

这些东西不是一个运行时配置就能完全兜住的。

所以工程上更准确的判断是：

```txt
qiankun 提供运行时隔离手段，但团队仍然要在编码规范、组件库配置和构建方案上控制样式边界。
```

---

## 11. 面试怎么回答

如果面试官问：

> qiankun 是怎么做样式隔离的？

可以这样回答：

```txt
qiankun 加载微应用时，会通过 import-html-entry 解析子应用 HTML，把里面的 CSS 资源拉取下来，并把外链 CSS 转成内联 style，再跟随子应用 wrapper 插入主应用指定容器。

默认情况下，它主要管理子应用样式的生命周期，也就是子应用挂载时样式进入页面，子应用卸载时样式随 wrapper 或动态样式副作用被清理、记录和重建。这个能力能减少单实例切换时的样式残留，但它不等于真正的样式作用域隔离。因为普通 CSS 只要进入同一个 document，选择器仍然可能匹配主应用或其他子应用的元素。

如果需要限制作用范围，qiankun 提供 experimentalStyleIsolation。它会给子应用容器加 data-qiankun 标记，并在运行时改写子应用 CSS 选择器，给规则加上容器前缀。这个方案对普通 class 冲突有帮助，但对 @keyframes、@font-face、@import、@page，以及弹窗挂到 body 这类场景支持有限。

qiankun 还提供 strictStyleIsolation，它基于 Shadow DOM。开启后，qiankun 会给微应用容器创建 shadowRoot，把子应用 DOM 和 style 放进去，利用浏览器原生能力做更强的样式隔离。但 Shadow DOM 需要适配，比如组件库弹层容器、全局主题、字体、document.querySelector 等都可能受影响。

所以真实项目里通常不会只依赖 qiankun 配置，还会结合 CSS 命名前缀、CSS Modules、组件库 prefixCls、构建期 scoped 样式等手段一起控制样式边界。
```

---

## 12. 本节总结

这一节带走四个判断。

第一：

```txt
DOM 容器不等于 CSS 作用域。
```

第二：

```txt
qiankun 默认管的是样式生命周期，不是样式作用范围。
```

第三：

```txt
experimentalStyleIsolation 的本质是选择器改写。
```

第四：

```txt
strictStyleIsolation 的本质是 Shadow DOM。
```

最后再收一句：

```txt
样式隔离不是背配置，而是先判断污染发生在哪一步，再选择合适的边界方案。
```
