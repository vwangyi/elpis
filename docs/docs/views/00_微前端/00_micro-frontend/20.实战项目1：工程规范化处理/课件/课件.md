# 搭建微前端 Monorepo 工程底座

## 1. Monorepo 与微前端

Monorepo 用一个仓库管理多个应用、共享包、依赖和工程任务。

微前端负责浏览器运行时的应用加载、组合、隔离、通信和路由协调。

```txt
Monorepo：代码与工程管理
微前端：运行时应用组合
```

建立 Monorepo 不等于完成微前端接入。

## 2. 目录边界

```txt
apps/
  README.md

packages/
  engineering-check/
    scripts/
      verify-environment.ts
    src/
      index.ts
    package.json

.husky/
  pre-commit
  commit-msg

.vscode/
  extensions.json
  settings.json

.editorconfig
.npmrc
.prettierignore
commitlint.config.mjs
eslint.config.mjs
lint-staged.config.mjs
package.json
pnpm-workspace.yaml
prettier.config.mjs
tsconfig.json
tsconfig.base.json
tsconfig.app.json
tsconfig.server.json
```

| 目录       | 内容                      | 判断标准                       |
| ---------- | ------------------------- | ------------------------------ |
| `apps`     | 前端应用、后端服务        | 可以独立启动、构建和部署       |
| `packages` | 工具、SDK、配置、共享模块 | 由其他工作区复用，不能独立部署 |

目录中存在 `package.json`，并且被工作区规则匹配后，才会成为 workspace package。README 文件不会让目录自动成为工作区包。

`engineering-check` 是最小验证包：

```txt
src/index.ts
  -> 模拟浏览器端 TypeScript 源码

scripts/verify-environment.ts
  -> 模拟 Node.js 工程脚本
```

没有真实复用需求时，不需要提前创建配置包或公共包。

## 3. 根项目配置

### 3.1 `package.json`

```json
{
  "private": true,
  "packageManager": "pnpm@10.33.0",
  "engines": {
    "node": ">=20.19.0",
    "pnpm": ">=10.0.0"
  }
}
```

| 配置             | 作用                       |
| ---------------- | -------------------------- |
| `private: true`  | 防止误发布 Monorepo 根项目 |
| `packageManager` | 记录包管理器及期望版本     |
| `engines.node`   | 声明 Node.js 版本范围      |
| `engines.pnpm`   | 声明 pnpm 版本范围         |

### 3.2 `pnpm-workspace.yaml`

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

这两条规则将 `apps` 和 `packages` 下的一级包纳入工作区。

### 3.3 `.npmrc`

```ini
auto-install-peers=true
link-workspace-packages=true
prefer-workspace-packages=true
strict-peer-dependencies=false
```

| 配置                             | 作用                                   |
| -------------------------------- | -------------------------------------- |
| `auto-install-peers`             | 自动安装 peer dependencies             |
| `link-workspace-packages`        | 优先链接仓库内的工作区包               |
| `prefer-workspace-packages`      | 优先使用工作区中的包                   |
| `strict-peer-dependencies=false` | peer dependency 不匹配时不直接阻止安装 |

关闭严格 peer dependency 检查会降低安装阻力，也会减弱依赖约束。生产项目应根据依赖治理要求决定是否开启严格检查。

## 4. 格式、代码质量与类型检查

| 工具       | 检查内容                             | 不负责         |
| ---------- | ------------------------------------ | -------------- |
| Prettier   | 缩进、引号、分号、换行、排版         | 代码质量和类型 |
| ESLint     | 未使用变量、不合理代码模式、团队规则 | 完整类型关系   |
| TypeScript | 类型关系、参数和返回值、模块类型     | 代码格式       |

### 4.1 Prettier

```js
export default {
  printWidth: 100,
  tabWidth: 2,
  useTabs: false,
  semi: false,
  singleQuote: true,
  trailingComma: "all",
  endOfLine: "lf",
};
```

`printWidth` 是换行参考值，不是强制最大字符数。

`.prettierignore` 通常排除依赖、构建产物、覆盖率结果和锁文件：

```txt
node_modules
dist
coverage
pnpm-lock.yaml
.pnpm-store
```

`.editorconfig` 统一编码、换行符、缩进和尾部空格等编辑器基础行为；Prettier 解析代码语法并重新排版。

### 4.2 ESLint

项目使用 Flat Config：

```txt
eslint.config.mjs
```

核心依赖：

| 包                       | 作用                          |
| ------------------------ | ----------------------------- |
| `eslint`                 | ESLint 核心和命令行           |
| `@eslint/js`             | JavaScript 推荐规则           |
| `typescript-eslint`      | 解析并检查 TypeScript         |
| `globals`                | 声明 Browser、Node 等全局变量 |
| `eslint-config-prettier` | 关闭与 Prettier 冲突的规则    |

`typescript-eslint` 不能代替 TypeScript 编译器。`eslint-config-prettier` 不会运行 Prettier。

项目规则包括：

```js
{
  '@typescript-eslint/consistent-type-imports': 'error',
  '@typescript-eslint/no-unused-vars': 'error',
  'no-console': 'warn',
}
```

仅作为类型使用的导入写成：

```ts
import type { OrderSummary } from "./order";
```

下划线前缀可以表示参数被有意保留但暂未使用：

```ts
function handleError(_error: Error) {}
```

`eslint-config-prettier` 放在配置数组末尾，用于覆盖前面与 Prettier 冲突的格式规则。

## 5. TypeScript 配置分层

```txt
tsconfig.json
  -> 仓库级入口
  -> 通过 references 组合多个检查目标

tsconfig.base.json
  -> 所有 TypeScript 代码共享的严格规则

tsconfig.app.json
  -> 浏览器端代码

tsconfig.server.json
  -> Node.js 服务和工程脚本
```

### 5.1 仓库入口

```json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.server.json" }
  ]
}
```

`files: []` 表示根配置不直接包含源码。`tsc -b` 会根据 `references` 检查各子项目。

### 5.2 共享规则

```json
{
  "compilerOptions": {
    "strict": true,
    "noImplicitOverride": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,
    "noEmit": true
  }
}
```

| 配置                               | 作用                                |
| ---------------------------------- | ----------------------------------- |
| `strict`                           | 开启严格类型检查                    |
| `noImplicitOverride`               | 重写父类成员时要求显式写 `override` |
| `noUncheckedIndexedAccess`         | 索引访问结果包含不存在的可能        |
| `exactOptionalPropertyTypes`       | 区分属性缺失与显式 `undefined`      |
| `forceConsistentCasingInFileNames` | 统一文件名大小写引用                |
| `skipLibCheck`                     | 跳过依赖声明文件内部检查            |
| `noEmit`                           | 只检查类型，不输出 JavaScript       |

### 5.3 浏览器端配置

浏览器端代码通常使用：

```txt
DOM 类型
ES Module
moduleResolution: Bundler
```

`moduleResolution: "Bundler"` 按现代打包器语义解析模块。TypeScript 负责类型检查，Vite 或 Webpack 负责构建。

### 5.4 Node.js 配置

Node.js 配置适用于：

- 后端服务
- Vite、Webpack 配置
- 构建和发布脚本
- 代码生成脚本

常用配置：

```json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "types": ["node"]
  }
}
```

## 6. 编辑器检查

VS Code 内置 TypeScript 语言服务，但不会自动执行项目中的 ESLint。

推荐扩展：

```txt
dbaeumer.vscode-eslint
esbenp.prettier-vscode
```

编辑器诊断用于提前发现问题，不能代替命令行、Git Hook 和 CI 检查。

## 7. Git 提交链路

```txt
Commitizen + cz-git
  -> 通过问答生成提交信息

Husky pre-commit
  -> lint-staged 检查暂存文件
  -> pnpm check 检查整个项目

Husky commit-msg
  -> commitlint 校验最终提交信息

检查全部通过
  -> 创建提交
```

| 工具        | 职责                           |
| ----------- | ------------------------------ |
| Husky       | 在 Git 生命周期中触发命令      |
| lint-staged | 处理本次暂存的文件             |
| Commitizen  | 提供交互式提交入口             |
| cz-git      | 提供提交类型、作用域和问题配置 |
| commitlint  | 校验最终提交信息               |

### 7.1 Git Hooks

`.husky/pre-commit`：

```sh
pnpm exec lint-staged
pnpm check
```

`.husky/commit-msg`：

```sh
pnpm exec commitlint --edit "$1"
```

任意命令失败都会阻止提交。

### 7.2 lint-staged

```js
export default {
  "*.{js,mjs,cjs,jsx,ts,mts,cts,tsx,vue}": ["eslint --fix", "prettier --write"],
  "*.{json,md,yaml,yml,css,scss,less,html}": ["prettier --write"],
};
```

| 命令          | 范围     | 自动修复 |
| ------------- | -------- | -------- |
| `lint-staged` | 暂存文件 | 是       |
| `pnpm check`  | 整个项目 | 否       |

### 7.3 提交信息

规范示例：

```txt
feat(order): 新增订单列表
fix(login): 修复登录失败问题
docs: 更新使用说明
```

执行提交向导：

```bash
pnpm commit
```

cz-git 负责生成，commitlint 负责最终校验。直接执行 `git commit -m` 仍会经过 commitlint。

本地 Hook 可以通过 `--no-verify` 跳过，因此远程 CI 仍需执行完整检查。

## 8. 统一工程命令

```json
{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "tsc -b",
    "check": "pnpm format:check && pnpm lint && pnpm typecheck",
    "commit": "cz",
    "prepare": "husky"
  }
}
```

| 命令                | 作用                             |
| ------------------- | -------------------------------- |
| `pnpm format`       | 修复格式                         |
| `pnpm format:check` | 检查格式，不修改文件             |
| `pnpm lint`         | 检查代码质量                     |
| `pnpm lint:fix`     | 修复可自动处理的 ESLint 问题     |
| `pnpm typecheck`    | 检查 TypeScript 类型             |
| `pnpm check`        | 依次执行格式、代码质量和类型检查 |
| `pnpm commit`       | 启动规范提交向导                 |

`pnpm check` 中任意一步失败，后续命令都会停止。

## 9. 验证配置是否生效

### 9.1 Prettier

制造不规范缩进或换行后执行：

```bash
pnpm format:check
pnpm format
```

第一条命令只报告问题，第二条命令修改文件。

### 9.2 ESLint

```ts
const unusedMessage = "eslint should report this";
```

执行：

```bash
pnpm lint
```

未使用变量应被报告为错误。

### 9.3 TypeScript

```ts
const orderAmount: number = "100";
```

执行：

```bash
pnpm typecheck
```

字符串不能赋值给数字类型，检查应失败。

验证后删除临时错误，执行：

```bash
pnpm check
```

## 10. 核心结论

1. Monorepo 管理仓库、依赖和工程任务；微前端管理浏览器运行时的应用组合。
2. `apps` 保存可独立运行和部署的应用，`packages` 保存供工作区复用的包。
3. Prettier 管格式，ESLint 管代码质量，TypeScript 管类型。
4. 根目录配置可以直接使用；出现稳定复用需求后再抽成配置包。
5. Husky 负责触发，lint-staged 负责暂存文件，cz-git 负责生成提交信息，commitlint 负责校验。
6. 配置是否有效必须通过实际命令和错误样例验证。
