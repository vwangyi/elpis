# 12. 微前端工程兜底

## 这节课要拿到什么结果

这一课只解决一个问题：某个子应用加载慢、加载失败或运行时报错时，主应用怎么避免整个系统白屏。

先记住一句话：

```txt
子应用失败应该是局部失败，不应该拖垮主应用。
```

你要拿到 5 个结论：

- 主应用要维护每个子应用的运行状态
- `loader` 只负责加载过程反馈，不等于完整错误兜底
- 加载失败和运行时异常都要落到主应用 fallback UI
- 重试不是刷新浏览器，不同接入方式的子应用重试策略不同
- 预加载能减少等待，但不能替代失败兜底

---

## 1. 为什么微前端更需要兜底

普通单体前端里，资源加载失败时，常见结果是整个应用进不来。

微前端不一样。主应用和子应用分开部署、分开加载，所以故障也可能是局部的。

比如：

```txt
主应用正常。
订单系统正常。
财务系统加载失败。
```

这时不应该让整个页面白屏。

更合理的结果是：

```txt
主应用导航仍然可用。
订单系统仍然可以进入。
财务区域显示服务不可用。
用户可以重新加载，也可以返回订单工作台。
```

白话说：

```txt
主应用不能只负责把子应用接进来，还要负责子应用出问题时系统怎么继续可用。
```

术语说：

```txt
这类能力通常叫工程兜底，包括 loading state、fallback UI、retry、timeout、global error handling 和 prefetch。
```

---

## 2. 先建子应用状态中心

要做兜底，主应用不能只知道当前路由。

它还要知道每个子应用现在是什么状态：

```txt
还没加载。
正在加载。
已经可用。
加载失败。
加载时间过长。
```

文件位置：`main-app/src/micro-app-status.mjs`

修改方式：`新建文件`

先定义状态枚举：

```js
export const MICRO_APP_STATUS = {
  IDLE: "idle",
  LOADING: "loading",
  READY: "ready",
  ERROR: "error",
  TIMEOUT: "timeout",
};
```

这些状态对应的意思是：

```txt
idle：还没开始加载。
loading：正在连接业务服务。
ready：业务服务已经可用。
error：业务服务加载失败或运行时报错。
timeout：加载时间过长，用户不能一直等。
```

状态中心不只保存状态，还要提供统一修改入口：

```js
statusStore.markLoading("finance");
statusStore.markReady("finance");
statusStore.markFailed("finance", error);
statusStore.prepareRetry("finance");
```

这样分工会清楚很多：

```txt
micro-apps.js 负责接收 qiankun、浏览器和子应用事件。
micro-app-status.mjs 负责整理状态变化。
App.vue 负责展示 loading、业务内容或兜底页。
```

如果没有状态中心，加载态、错误态、重试次数、超时计时器就会散落在多个文件里，后面很难判断当前子应用到底还能不能用。

## 3. 用 loader 接住加载态

`loader` 是 qiankun 在子应用加载状态变化时调用的函数。

白话说：

```txt
它告诉主应用：子应用开始加载了，或者加载结束了。
```

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

主应用里创建状态中心：

```js
const statusStore = createMicroAppStatusStore({
  apps: microApps,
  minLoadingMs: 6000,
  stateFactory: reactive,
});

export const microAppStatus = statusStore.state;
```

这里传 `reactive`，是为了让 Vue 页面能自动响应状态变化。

再封装 loader：

```js
function createLoader(appName) {
  return (loading) => {
    if (loading) {
      statusStore.markLoading(appName);
      return;
    }

    statusStore.markReady(appName);
  };
}
```

财务系统是 `registerMicroApps` 注册的，可以直接配置 loader：

```js
registerMicroApps([
  {
    name: microApps.finance.name,
    entry: microApps.finance.entry,
    container: "#normal-subapp-viewport",
    activeRule: microApps.finance.activeRule,
    props: createRouteProps(router, microApps.finance),
    loader: createLoader("finance"),
  },
]);
```

订单系统不一样。

订单是 `loadMicroApp` 手动加载并保活的，不能只靠注册配置里的 `loader`。主应用要在手动加载前后自己改状态：

```js
statusStore.markLoading("order");

orderMicroApp = loadMicroApp({
  name: microApps.order.name,
  entry: microApps.order.entry,
  container: "#order-viewport",
  props: createOrderProps(router, true),
});

orderMicroApp.mountPromise
  .then(() => statusStore.markReady("order"))
  .catch((error) => statusStore.markFailed("order", error));
```

注意：

```txt
loader 不是错误处理。
loader 只能告诉主应用加载中或加载结束。
失败以后怎么展示，仍然要主应用自己处理。
```

## 4. 主应用展示加载态和兜底页

文件位置：`main-app/src/App.vue`

修改方式：`局部修改`

主应用引入状态：

```js
import {
  getLastVisitedPath,
  getMicroApps,
  microAppStatus,
  MICRO_APP_STATUS,
  retryMicroApp,
} from "./micro-apps";
```

根据当前路由判断当前子应用：

```js
const currentAppKey = computed(() => {
  if (route.path.startsWith("/finance") && microApps.finance) {
    return "finance";
  }
  return "order";
});

const currentAppStatus = computed(() => microAppStatus[currentAppKey.value]);
```

正在加载时，显示加载遮罩：

```vue
<section v-if="isCurrentAppLoading" class="service-mask">
  <div class="service-card service-card-loading">
    <span class="eyebrow eyebrow-main">连接中</span>
    <h2>{{ currentAppStatus.message }}</h2>
    <p>正在连接业务服务，请稍候。</p>
  </div>
</section>
```

加载失败或运行时报错时，显示兜底页：

```vue
<section v-if="isCurrentAppUnavailable" class="service-mask">
  <div class="service-card service-card-error">
    <button
      class="service-close-button"
      type="button"
      aria-label="关闭服务提示"
      @click="closeCurrentFallback"
    >
      ×
    </button>

    <span class="eyebrow eyebrow-main">服务不可用</span>
    <h2>{{ currentAppStatus.message }}</h2>
    <p>{{ currentAppStatus.detail || "当前业务服务暂时无法响应。" }}</p>

    <div class="service-actions">
      <button type="button" @click="retryCurrentApp">重新加载</button>
      <button type="button" class="secondary" @click="backToWorkspace">
        返回订单工作台
      </button>
    </div>
  </div>
</section>
```

兜底页不要只写一句“加载失败”。

它至少要解决三个问题：

```txt
告诉用户哪个业务服务不可用。
给用户重新加载入口。
给用户离开故障业务的路径。
```

右上角关闭按钮只表示“关闭当前提示”，不表示子应用已经恢复。

## 5. 接住加载失败和运行时错误

子应用失败可能发生在两个阶段。

第一类是加载阶段失败：

```txt
子应用服务没启动。
entry 请求失败。
JS 或 CSS 资源请求失败。
```

这时子应用可能还没运行，只有主应用能显示兜底页。

第二类是运行阶段失败：

```txt
子应用已经挂载成功。
内部某个关键业务能力不可用。
子应用需要通知主应用整块降级。
```

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

主应用集中注册三类错误入口：

```js
function registerGlobalErrorHandler() {
  if (globalErrorHandlerRegistered) return;

  addGlobalUncaughtErrorHandler((event) => {
    markCurrentAppFailed(event?.reason || event?.message || event);
  });

  window.addEventListener("micro-app:business-error", markReportedAppFailed);

  window.addEventListener("error", (event) => {
    if (!window.location.pathname.startsWith("/finance")) return;
    event.preventDefault?.();
    markCurrentAppFailed(event.error || event.message || event);
  });

  window.addEventListener("unhandledrejection", (event) => {
    if (!window.location.pathname.startsWith("/finance")) return;
    event.preventDefault?.();
    markCurrentAppFailed(event.reason || event);
  });

  globalErrorHandlerRegistered = true;
}
```

这三层入口分别处理：

```txt
qiankun 全局未捕获异常。
子应用主动上报的业务异常。
浏览器层面的 error 和 unhandledrejection。
```

它们只负责发现错误，最后都调用 `statusStore.markFailed()`。

这样 `App.vue` 不需要关心错误来自哪里，只需要根据状态展示兜底页。

## 6. 子应用主动上报业务异常

不是所有业务不可用都会变成未捕获 JS 异常。

比如财务系统调用支付通道失败，子应用通常会自己 `try...catch`。既然异常已经被捕获，就不会自然进入全局未捕获错误监听。

所以更合理的做法是：

```txt
子应用捕获异常。
子应用判断这个异常是否影响整个业务模块。
如果需要整块降级，就通过约定通道告诉主应用。
主应用统一显示兜底页。
```

文件位置：`finance-app/src/App.jsx`

修改方式：`局部修改`

财务子应用上报业务异常：

```jsx
function reportPaymentChannelError() {
  window.dispatchEvent(
    new CustomEvent("micro-app:business-error", {
      detail: {
        appName: "finance",
        message: "财务支付通道响应异常",
      },
    }),
  );
}
```

页面按钮只保留业务动作：

```jsx
<button
  className="finance-action finance-action-secondary"
  type="button"
  onClick={reportPaymentChannelError}
>
  上报支付通道异常
</button>
```

这里不要用 `throw new Error()` 当主案例。

原因是开发服务器的错误覆盖层可能会盖住页面，学生看到的是开发工具报错，不是主应用兜底。

相关配置是：

```js
// main-app/webpack.config.cjs
// order-app/webpack.config.cjs
devServer: {
  client: {
    overlay: false,
  },
}
```

```js
// finance-app/vite.config.js
server: {
  hmr: {
    overlay: false,
  },
}
```

这两个配置只关闭开发工具自己的全屏遮罩，不会替代主应用兜底逻辑。

## 7. 重试不是刷新整个系统

重试不应该要求用户刷新浏览器。

它应该由主应用重新尝试加载当前子应用，同时保住主应用和其他业务状态。

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

重试前先清理旧状态：

```js
statusStore.prepareRetry(appName);
```

订单系统是 `loadMicroApp` 手动保活实例。

重试订单时，要先卸载旧实例：

```js
if (appName === "order") {
  await orderMicroApp?.unmount?.();
  orderMicroApp = null;
}
```

财务系统是 `registerMicroApps` 自动调度的应用。

如果第一次进入财务时服务没启动，后面服务启动后，不能只靠切路由再切回来。更明确的做法是：

```txt
主应用先探测财务 entry 是否可访问。
不可访问：直接显示 fallback。
可访问：打开财务加载开关。
当前路由不变时，用 single-spa 的 triggerAppChange() 原地重新调度。
```

关键函数是：

```js
async function ensureFinanceCanLoad(path) {
  if (!isFinancePath(path) || financeLoadEnabled) return;

  const checkVersion = ++financeCheckVersion;
  statusStore.markLoading("finance");

  try {
    const response = await fetch(getEntryUrl(microApps.finance.entry), {
      cache: "no-store",
    });

    if (!response.ok) {
      throw new Error(`财务系统入口请求失败：${response.status}`);
    }

    if (checkVersion !== financeCheckVersion) return;

    financeLoadEnabled = true;
    await nextTick();
    await triggerAppChange();
  } catch (error) {
    if (checkVersion !== financeCheckVersion) return;

    financeLoadEnabled = false;
    statusStore.markFailed("finance", error);
  }
}
```

这里的重点不是 `fetch` 本身，而是重试链路：

```txt
先确认入口能访问。
再允许 qiankun 加载。
当前 URL 没变时，主动触发 single-spa 重新调度。
```

`single-spa` 要显式安装到主应用依赖里，因为代码直接使用了它的 API：

```js
import { triggerAppChange } from "single-spa";
```

`triggerAppChange()` 的作用是让 single-spa 重新检查当前 URL，判断哪些应用应该加载、挂载或卸载。

## 8. 保活实例 update 要等挂载完成

订单系统用了 `loadMicroApp()` 做保活。

`loadMicroApp()` 返回的是 single-spa 的 parcel 实例。

白话说：

```txt
parcel 就是主应用手动持有的一块微应用实例。
```

它有 `mountPromise`、`update()`、`unmount()`、`getStatus()` 等方法。

注意：

```txt
只有 parcel 进入 MOUNTED 状态后，才可以调用 update()。
```

如果实例还没挂载完成就调用 `update()`，可能出现：

```txt
single-spa minified message #32
```

这个错误不是订单服务不可用，而是主应用调用保活实例的时机太早。

所以要先判断实例状态：

```js
function isMountedMicroApp(microApp) {
  return microApp?.getStatus?.() === "MOUNTED";
}

function updateOrderMicroApp(router, keepAliveActive) {
  if (!isMountedMicroApp(orderMicroApp)) return;

  orderMicroApp
    .update?.(createOrderProps(router, keepAliveActive))
    ?.catch?.((error) => {
      if (String(error?.message || error).includes("code=32")) return;
      statusStore.markFailed("order", error);
    });
}
```

再把直接调用 `update()` 的地方改成：

```js
updateOrderMicroApp(router, true);
updateOrderMicroApp(router, false);
```

这一段要记住的是：

```txt
loadMicroApp 给了主应用手动控制权。
主应用拿到控制权以后，也要负责判断实例当前能不能被 update。
```

## 9. 超时不是失败判断

很多人会把“超时”理解成“服务一定挂了”。

这个理解不准确。

白话说：

```txt
超时不是证明服务失败。
超时只是说明用户不能一直等。
```

文件位置：`main-app/src/micro-app-status.mjs`

修改方式：`局部修改`

状态中心里给加载过程设置超时：

```js
appStatus.timeoutId = setTimer(() => {
  appStatus.status = MICRO_APP_STATUS.TIMEOUT;
  appStatus.message = `${appStatus.label}加载时间过长`;
  appStatus.detail = "服务仍在连接中，可以继续等待，或先处理其他业务。";
  appStatus.error = "timeout";
  appStatus.timeoutId = null;
}, timeoutMs);
```

这里的意思是：

```txt
超过指定时间还没完成加载，主应用先给用户明确反馈。
```

但真实请求不一定已经停止，子应用后面仍然可能加载成功。

所以超时兜底应该给用户退路：

```txt
继续等待。
重新加载。
先返回其他业务。
```

## 10. 预加载减少高频系统等待

预加载解决的是另一个问题：

```txt
常用子应用第一次进入太慢，能不能提前准备资源？
```

白话说：

```txt
预加载就是用户还没点击时，主应用先把后面可能用到的子应用资源请求回来。
```

它不是提前挂载子应用。

```txt
prefetch 会提前请求资源。
prefetch 不会提前执行子应用 mount。
```

本节订单系统是高频核心工作台，但订单不是 `registerMicroApps` 注册的，而是 `loadMicroApp` 手动保活的。

所以不能只写：

```js
start({
  prefetch: [microApps.order.name],
});
```

因为订单不在注册列表里，这个名字匹配不到订单。

正确做法是显式调用 `prefetchApps()`：

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

```js
start({
  ...qiankunSandboxOptions,
  prefetch: false,
});

prefetchApps([{ name: microApps.order.name, entry: microApps.order.entry }]);
```

这里要分清楚两件事：

```txt
订单：启动后预加载资源，减少高频系统等待。
财务：进入财务路径后探测 entry 是否可访问，不是预加载。
```

预加载不是越多越好。

更合理的策略是：

```txt
高频、核心、体积可控的子应用优先预加载。
低频、体积大、权限命中率低的子应用不要无脑预加载。
```

注意：

```txt
预加载只能减少等待，不能保证子应用一定可用。
服务挂了、资源 404、运行时报错，仍然要靠前面的兜底逻辑。
```

## 11. 面试怎么回答

如果面试官问：

> 微前端里某个子应用加载失败，你们怎么处理？

可以这样回答：

```txt
主应用会把子应用失败当成局部故障处理，不会让整个系统白屏。

我们会维护每个子应用的运行状态，比如 idle、loading、ready、error、timeout。qiankun 的 loader 用来更新加载状态；全局错误监听、浏览器 error、unhandledrejection 和子应用主动上报，用来把失败统一落到状态中心。

页面上不会只打印错误，而是显示业务化兜底页。比如财务系统不可用时，主应用壳层和订单系统仍然可用，财务区域显示服务不可用、重新加载和返回订单工作台。

重试时要看子应用接入方式。loadMicroApp 手动保活的应用要先处理旧实例；registerMicroApps 自动调度的应用可以配合 entry 探测和 triggerAppChange 重新调度。

高频核心子应用可以做预加载，但预加载只减少等待，不能替代错误兜底。线上还要配合错误上报、版本号、entry 地址和当前路径来定位问题。
```

## 14. 本节总结

这一课记住五句话：

```txt
子应用失败应该是局部失败，不应该拖垮主应用。
loader 解决加载过程反馈，不是完整错误兜底。
兜底页要给用户继续操作的路径。
超时不是证明服务失败，而是用户不能无限等待。
预加载解决首次进入慢，不能替代失败兜底。
```

最后一句：

```txt
微前端工程兜底的目标，不是让每个子应用永远不出错，而是让局部错误可见、可控、可恢复。
```
