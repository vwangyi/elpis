# 08. 路由保持与 keep alive

## 这节课要拿到什么结果

这一课解决两个问题：

- 切到别的子系统后，再切回来，还能回到上次访问的子路由
- 切走订单系统后再回来，订单详情页里未提交的表单内容还在

先把两个概念分清楚：

- 路由保持：回来时地址对，比如回到 `/orders/detail/2048`
- keep alive：回来时页面运行现场还在，比如输入框里的内容没有丢

路由保持不等于 keep alive。地址恢复了，只能说明“回到了同一个页面地址”；表单、滚动、弹窗、定时器这些现场是否还在，要看应用实例有没有被销毁。

本节示例里会形成一个对比：

- 订单子应用：用 `loadMicroApp` 手动持有实例，切走时隐藏，不卸载
- 财务子应用：继续用 `registerMicroApps` 自动调度，离开后正常卸载

---

## 1. 路由保持：主应用记录每个子系统的最近路径

### 1.1 思路

微前端页面里，真正一直存在的是主应用。子应用可能被挂载、卸载、隐藏或重建，所以“最近访问到哪个子路由”应该放在主应用里记。

比如用户的访问链路是：

```txt
/orders/detail/2048
  -> /finance/refund/1024
  -> /orders/detail/2048
```

主应用需要分别记住：

- 订单系统最近路径：`/orders/detail/2048`
- 财务系统最近路径：`/finance/refund/1024`

下次点击左侧菜单时，不再固定跳默认首页，而是跳这个子系统的最近路径。

### 1.2 修改主应用微前端注册文件

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

先在主应用里保存每个子系统的默认路径和最近路径：

```js
const lastVisitedPaths = {
  order: microApps.order.defaultPath,
  finance: microApps.finance.defaultPath,
};
```

再根据浏览器路径判断当前属于哪个子系统：

```js
function getAppNameByPath(path) {
  if (path.startsWith(microApps.finance.activeRule)) return "finance";
  return "order";
}
```

每次主应用路由变化后，更新当前子系统的最近路径：

```js
function rememberVisitedPath(path) {
  const appName = getAppNameByPath(path);
  lastVisitedPaths[appName] = path || microApps[appName].defaultPath;
}
```

把最近路径导出去，给菜单使用：

```js
export function getLastVisitedPath(appName) {
  return lastVisitedPaths[appName] || microApps[appName]?.defaultPath || "/";
}
```

最后在主应用路由后置钩子里记录路径：

```js
router.afterEach((to) => {
  rememberVisitedPath(to.path);
  syncOrderKeepAlive(router, to.path);
});
```

这里的 `to.path` 是浏览器真实路径。订单子应用内部点击详情页后，最终也要让主应用执行 `router.push()`，这样主应用才能在 `afterEach` 里记录到正确路径。

### 1.3 修改主应用菜单

文件位置：`main-app/src/App.vue`

修改方式：`局部修改`

引入最近路径读取方法：

```js
import { getLastVisitedPath, getMicroApps } from "./micro-apps";
```

菜单项里保留业务键。注意：`name` 是 qiankun 注册名，比如 `order-app`；`appKey` 是课程里用来记录最近路径的业务键，比如 `order`。

```js
const menuItems = [
  { ...microApps.order, appKey: "order" },
  { ...microApps.finance, appKey: "finance" },
].filter(Boolean);
```

菜单跳转目标改成最近访问路径：

```js
function getMenuPath(appName) {
  return getLastVisitedPath(appName);
}
```

模板里使用 `getMenuPath(item.appKey)`：

```vue
<RouterLink
  v-for="item in menuItems"
  :key="item.name"
  class="menu-button"
  :class="{ active: currentAppKey === item.appKey }"
  :to="getMenuPath(item.appKey)"
>
  <strong>{{ item.label }}</strong>
</RouterLink>
```

这一段完成后，点击“订单子应用”时，主应用会跳到订单最近访问路径，而不是每次都跳 `/orders/list`。

## 2. 子应用内部导航为什么要告诉主应用

前一课已经把子应用改成了嵌入态 `memory router`。它的好处是：子应用内部跳转不再直接写浏览器地址栏，避免和主应用抢 `window.history`。

但这样会带来一个问题：子应用内部路由变了，主应用怎么知道？

答案是：子应用不要自己改真实 URL，而是调用主应用传下来的 `navigate(path)`。

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

主应用传给子应用统一导航协议：

```js
function createRouteProps(router, microApp) {
  return {
    defaultPath: microApp.defaultPath,
    getCurrentPath: () => window.location.pathname,
    navigate: (path) => {
      const targetPath = path || microApp.defaultPath;
      if (router.currentRoute.value.path !== targetPath) {
        void router.push(targetPath);
      }
    },
  };
}
```

链路是这样的：

```txt
用户点击子应用内部菜单
  -> 子应用调用 props.navigate("/orders/detail/2048")
  -> 主应用 router.push("/orders/detail/2048")
  -> 主应用 afterEach 记录 to.path
  -> lastVisitedPaths.order = "/orders/detail/2048"
```

一句话：主应用不是监听子应用的 `memory router`，而是让子应用通过 `navigate(path)` 申请跳转。真实 URL 仍然由主应用统一修改。

## 3. keep alive：保住的是应用实例，不只是路径

### 3.1 常见方案

keep alive 常见有三类做法。

第一类是状态持久化。

白话解释：应用可以销毁，但销毁前把关键数据存起来，回来时再填回去。

常见位置有：Pinia、Redux、`sessionStorage`、IndexedDB、后端草稿接口。

它适合保存表单草稿、筛选条件、搜索条件。但页面实例已经销毁过，所以它不是应用级 keep alive。

第二类是 iframe 不销毁。

白话解释：子系统放在 iframe 里，切走时只隐藏 iframe，不销毁 iframe。

它对老系统很直接，但主应用对 iframe 内部控制弱，权限、通信、埋点、样式统一都会更麻烦。

第三类是应用级 keep alive。

白话解释：第一次进入订单系统时加载订单子应用；切到财务时，不卸载订单子应用，只把它隐藏；再切回来时，继续显示原来的订单实例。

这一课采用第三类方案。

### 3.2 为什么用 loadMicroApp

先区分两个 qiankun API。

`registerMicroApps` 是自动调度：

```txt
URL 命中 activeRule -> mount
URL 离开 activeRule -> unmount
```

它适合普通子应用接入。

但订单系统要保活，离开 `/orders` 时不能自动 `unmount`，所以订单不能继续完全交给 `registerMicroApps`。

`loadMicroApp` 是手动加载：

```js
import { loadMicroApp } from "qiankun";

const orderMicroApp = loadMicroApp({
  name: "order-app",
  entry: "//localhost:5174",
  container: "#order-viewport",
  props: {
    activePath: "/orders/detail/2048",
    keepAliveActive: true,
  },
});
```

注意：`loadMicroApp` 本身不是“保活开关”。

真正的保活来自这条约定：

```txt
第一次进入订单 -> loadMicroApp 创建实例
切到财务 -> 不调用 unmount，只隐藏订单容器
再切回订单 -> 显示原容器，复用原实例
```

## 4. 修改主应用：订单手动保活，财务自动调度

### 4.1 订单用 loadMicroApp

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

引入 `loadMicroApp`：

```js
import { loadMicroApp, registerMicroApps, start } from "qiankun";
```

准备订单实例变量：

```js
let orderMicroApp = null;
```

封装订单 props：

```js
function createOrderProps(router, keepAliveActive) {
  return {
    ...createRouteProps(router, microApps.order),
    activePath: getLastVisitedPath("order"),
    keepAliveActive,
  };
}
```

这里有两个字段要记住：

- `activePath`：告诉订单子应用应该显示哪个内部路由
- `keepAliveActive`：主应用和订单子应用约定的显示/隐藏状态，不是 qiankun 内置字段

第一次显示订单时，加载订单子应用：

```js
function showOrderMicroApp(router) {
  if (!orderMicroApp) {
    orderMicroApp = loadMicroApp({
      name: microApps.order.name,
      entry: microApps.order.entry,
      container: "#order-viewport",
      props: createOrderProps(router, true),
    });
    return;
  }

  orderMicroApp.update?.(createOrderProps(router, true));
}
```

切走订单时，只通知它进入隐藏态，不卸载实例：

```js
function hideOrderMicroApp(router) {
  orderMicroApp?.update?.(createOrderProps(router, false));
}
```

这就是保活关键：没有调用 `orderMicroApp.unmount()`。

### 4.2 财务继续 registerMicroApps

文件位置：`main-app/src/micro-apps.js`

修改方式：`局部修改`

订单已经交给 `loadMicroApp` 手动管理，所以 `registerMicroApps` 里只保留财务：

```js
registerMicroApps([
  {
    name: microApps.finance.name,
    entry: microApps.finance.entry,
    container: "#normal-subapp-viewport",
    activeRule: microApps.finance.activeRule,
    props: createRouteProps(router, microApps.finance),
  },
]);
```

这样两个子应用的管理方式就不同了：

- 订单：主应用手动加载，切走不卸载
- 财务：qiankun 自动调度，离开后卸载

## 5. 修改主应用页面：订单容器必须常驻

### 5.1 订单容器

文件位置：`main-app/src/App.vue`

修改方式：`局部修改`

主应用工作区里保留订单容器：

```vue
<main class="workspace">
  <div v-show="currentAppKey === 'order'" id="order-viewport"></div>
  <RouterView v-show="currentAppKey !== 'order'" />
</main>
```

这里必须用 `v-show`，不能用 `v-if`。

白话解释：`v-show` 只是显示和隐藏，DOM 还在；`v-if` 会创建和销毁 DOM。

订单子应用挂在 `#order-viewport` 上。如果这个容器被销毁，保活实例就没有稳定的挂载位置了。

### 5.2 普通子应用容器

文件位置：`main-app/src/components/RoutePortal.vue`

修改方式：`局部修改`

普通子应用容器改成：

```vue
<template>
  <section>
    <article class="panel">
      <div class="subapp-host" id="normal-subapp-viewport"></div>
    </article>
  </section>
</template>
```

此时主应用里有两个容器：

- `#order-viewport`：给订单保活实例使用
- `#normal-subapp-viewport`：给财务这类普通子应用使用

## 6. 修改订单子应用：接收主应用 update

文件位置：`order-app/src/main.js`

修改方式：`局部修改`

订单子应用嵌入主应用时继续使用 `memory router`：

```js
router = createOrderRouter(
  isEmbedded ? createMemoryHistory() : createWebHashHistory(),
);
```

然后补一个同步路径方法：

```js
async function syncActivePath(path) {
  if (!router || !path || router.currentRoute.value.fullPath === path) return;
  await router.push(path);
}
```

它的作用是：主应用真实 URL 变化后，订单内部的 `memory router` 也切到对应页面。

再导出 `update` 生命周期：

```js
export async function update(props = {}) {
  latestProps = {
    ...latestProps,
    ...props,
  };

  await syncActivePath(
    latestProps.activePath || latestProps.getCurrentPath?.(),
  );
  syncKeepAliveState(latestProps);
}
```

`update()` 的作用是：订单实例已经存在时，主应用不用重新 `mount`，而是把新的 props 发给这个实例。

这里还可以根据显示/隐藏状态处理副作用：

```js
function syncKeepAliveState(props = {}) {
  if (props.keepAliveActive === false) {
    console.info(
      "[order-app] keep alive inactive: pause polling or subscriptions here",
    );
    return;
  }

  if (props.keepAliveActive === true) {
    console.info(
      "[order-app] keep alive active: resume visible workspace work here",
    );
    syncDocumentTitle();
  }
}
```

真实项目里，这里可以暂停或恢复：

- 轮询
- WebSocket 订阅
- 定时器
- 页面可见时才需要跑的数据刷新

## 9. 重要边界：子系统保活不等于页面组件都保活

当前实现保住的是订单子应用实例。

也就是说：

```txt
订单详情输入表单
  -> 切到财务系统
  -> 再切回订单系统
  -> 表单内容还在
```

但如果用户一直停留在订单子应用内部，从订单详情切到另一个订单页面，再切回订单详情：

```txt
/orders/detail/2048
  -> /orders/refund/1024
  -> /orders/detail/2048
```

订单详情里的组件内 `ref` 状态默认可能会丢。

原因是：

- `loadMicroApp` 保住的是整个订单子应用实例
- 订单子应用内部的 `RouterView` 仍然由 Vue Router 管理
- 从详情页切到其他页面时，详情组件可能会被 Vue Router 卸载
- 再切回详情页时，详情组件重新创建，组件内 `ref` 会重新初始化

如果真实项目还要求子应用内部页面来回切换时也保住状态，需要在子应用内部再做页面级缓存或状态管理。常见做法是：

- 用 Vue 的 `<KeepAlive>` 包住需要缓存的 `RouterView` 页面
- 把草稿放到 Pinia、组件外 store、`sessionStorage` 或后端草稿接口里

这属于子应用内部页面级状态管理，不是 qiankun 的 `loadMicroApp` 自动解决的范围。

---

## 10. 本节最后记住什么

这一课记住 4 句话：

1. 路由保持解决的是“切回来在哪个子路由”。
2. keep alive 解决的是“切回来时页面运行现场还在不在”。
3. `registerMicroApps` 适合普通路由驱动接入，但离开 `activeRule` 后会自动卸载。
4. `loadMicroApp` 不是保活开关，但它能让主应用手动持有子应用实例，是实现应用级 keep alive 的关键 API。
