# 02. 微前端的实现方案

## 这节课解决两个问题

上节课我们已经给微前端下了定义：

微前端就是把一个很大的前端系统，按业务拆成几个前端项目。每个项目可以分别开发、分别迭代，最后再把它们组织成一个完整系统给用户使用。

我们把这个定义分拆一下，其实就解决两个问题：

第一，微前端该怎么拆。

第二，拆完以后怎么把子应用接进系统。

---

## 1. 微前端不是拆页面，而是拆业务

做微前端时，最容易犯的错就是把注意力放在页面数量上。

页面多，不代表就该拆。

真正该先看的，是业务边界。

如果一个系统本来就已经分成了用户、商品、订单、财务这些长期独立运转的业务块，第一版拆分通常就应该顺着这条边界走。

也就是说：

- 用户业务归用户应用
- 商品业务归商品应用
- 订单业务归订单应用
- 财务业务归财务应用

这样拆最自然。团队分工、需求流转、上线节奏，通常本来就是按这条线在走。

所以微前端不是把一个系统切成很多小页面。

微前端先做的，是把大业务边界划清楚。

---

## 2. 真碰到交叉页面，只问三件事

难点通常不在大块业务怎么拆，而在少量交叉页面怎么判断。

比如：

- 订单详情里带发票信息，这页归谁
- 退款既有售后流程，又有打款动作，这页归谁
- 首页看板里有经营分析内容，这页归谁

遇到这种页面，不用先争概念，先问三件事：

- 这个页面最主要是让用户完成什么动作
- 这个页面最关键的业务规则归谁定
- 这个页面出了问题，最后谁兜底

如果这三件事里，有两件甚至三件都指向同一个业务，这个页面通常就归那个业务。

这套判断法很实用，因为它抓的是业务责任，不是页面长相。

---

## 3. 只看一个典型例子：退款

退款看起来像一件事，实际经常是两段业务。

前半段更像订单：

- 为什么退
- 审核过没过
- 货退回来没有

后半段更像财务：

- 退多少钱
- 怎么打款
- 到账没有

所以退款最稳的拆法，往往不是硬塞给一个应用，而是把售后流程放在订单，把退款执行放在财务。

这件事很重要，因为它能说明一个常见误区：同一个词，不一定只对应一个业务节点。

---

## 4. 边界定完了，下一步才是怎么接进系统

假设现在已经拆出了三个前端项目：

- 主应用
- 订单子应用
- 财务子应用

接下来要解决的问题就变成了：

主应用到底用什么方式，把订单和财务接进来？

常见做法可以先看三种：

- 直接链接跳转
- iframe
- JavaScript 运行时接入

这三种方式的区别，不在页面内容，而在“这些页面到底是怎么被组织到一起的”。

---

## 5. 第一种方式：直接链接跳转

这是最简单的一种。

主页面不真正接管子页面，只是放几个入口链接，点到哪个，就跳到哪个系统。

它的优点很直接：

- 实现最简单
- 每个系统最独立

问题也很直接：

- 切换体验很割裂
- 更像多个站点互相跳，不像一个完整系统

所以它可以作为最小起点，但一般不会被当成“真正的微前端体验”。

---

## 6. 第二种方式：iframe

这是很多人最先想到的方案。

做法也容易理解：主应用先把菜单、导航、布局搭好，再在中间留一块区域，把订单页或者财务页装进去。

为什么它第一眼很像微前端？

因为它确实已经有了“统一外壳 + 可切换业务区”这个样子。

### 6.1 iframe 的优点

- 很直观，容易理解
- 隔离性强，子应用之间不容易直接互相影响
- 技术栈不统一时也比较容易接进来
- 旧系统改造成本相对低

这里的“隔离性强”不是一句空话。

iframe 里本来就是一个独立页面，它有自己的运行环境、自己的样式范围、自己的页面结构。正因为隔得开，所以旧系统更容易先挂进来。

### 6.2 iframe 的问题

iframe 不是不能用。

它真正的问题是：刚开始看起来很顺，页面和交互一复杂，别扭的地方会越来越多。

最常见的是这几类：

- UI的割裂感重
  - 嵌套感重，像系统里又装了一个小系统
  - 容易出现双滚动，主页面和子页面都在滚

- 每切一次都像重新开一个独立页面，性能开销更大
- 子应用的路由状态不容易和主应用地址栏同步
- 弹窗、遮罩、抽屉这类浮层，常常只能盖住 iframe 自己那块区域
- 主应用和子应用通信时，往往要额外搭消息桥

最后这一点尤其关键。

因为 iframe 里的页面和外面的主应用，不在同一个运行时里。很多事情不能像普通组件通信那样直接做，通常要靠额外消息机制，比如 postMessage。

这就意味着：

不是做不到，而是每做一步协作，都要额外补一层通信设计。

所以，上一课留下来的那个问题，现在可以直接给出答案：

如果用 iframe 做微前端，它的优点是直观、隔离强、老系统容易接；它的缺点是嵌套感、滚动、路由、弹窗和通信这些问题会越来越明显。

---

## 7. 第三种方式：JavaScript 运行时接入

如果不想只是跳页面，也不想把一个完整页面塞进 iframe，常见的下一步就是运行时接入。

它的核心不是再放一个页面进去，而是：

主应用在运行时把子应用代码加载进来，再让子应用把界面挂到主应用指定的容器里。

可以把它理解成两步：

- 主应用决定现在该显示谁
- 子应用按约定挂载到主应用给出的容器里

这就是后面常会听到的两个词：

- mount：挂载
- unmount：卸载

为什么这种方式更像真正的微前端？

因为主应用保留的是统一外壳，子应用接进来的是自己的业务能力，不是整个完整页面的壳子。

这样一来，系统看起来会更像一个整体。

### 7.1 它的优点

- 一体化体验更自然，没有 iframe 那种明显的套娃感
- 路由、权限、通知、全局状态这类协作更容易统一起来
- 页面切换更顺，主应用能自己控制加载、卸载和过渡过程
- 更接近后面真实微前端框架的主线

### 7.2 它的代价

- 没有 iframe 那种天然强隔离，样式和全局变量需要自己治理
- 主应用和子应用必须提前约定生命周期
- 路由边界、状态边界、样式边界都要自己设计
- 老项目改造成这种模式，成本通常高于 iframe

所以它不是“最省事”的方案。

它只是把成本放到了更值得长期投入的地方。

------



## 8. 小结

微前端先解决的是“怎么按业务拆”，不是“怎么把页面拆碎”。

交叉页面不要靠感觉分，先看动作、规则和兜底责任归谁。

接入方式上，直接跳转最简单，iframe 最直观但问题也最容易堆出来，运行时接入更像真正的一体化微前端。

后面的实战，会继续围绕第三种方式展开。
