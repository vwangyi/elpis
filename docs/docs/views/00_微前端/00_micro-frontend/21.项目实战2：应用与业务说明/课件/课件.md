# 20. 独立应用完成后，微前端还要解决什么

## 1. 当前系统

系统包含四个可以独立运行的应用：

| 应用              | 技术栈 | 职责                       | 微前端角色 |
| ----------------- | ------ | -------------------------- | ---------- |
| `portal-shell`    | Vue    | 登录、全局入口、经营指标   | 主应用候选 |
| `fulfillment-app` | Vue    | 审核、发运、签收、异常处理 | 子应用候选 |
| `settlement-app`  | React  | 对账、开票、付款           | 子应用候选 |
| `api-server`      | NestJS | 业务接口与数据访问         | 后端服务   |

业务链路：

```txt
销售订单
  -> 履约审核
  -> 发运与签收
  -> 结算对账
  -> 开票与付款
```

这些应用位于同一个仓库，并且读取同一套后端数据，但仍不是微前端系统。

```txt
同一个 Monorepo ≠ 同一个浏览器运行时
同一个数据库    ≠ 前端应用间通信
多个独立 SPA    ≠ 微前端系统
```

## 2. 共享配置为什么现在抽成包

只有一个消费者时，ESLint 和 TypeScript 配置放在根目录即可。出现 Vue、React、NestJS 等多个消费者后，配置既有公共规则，也有技术栈差异。

```txt
全部写在根目录
  -> 根配置需要了解所有应用细节

每个应用复制一份
  -> 规则升级时需要重复修改

提取为配置包
  -> 公共规则复用，应用保留局部差异
```

### 2.1 ESLint 分层

```txt
packages/eslint-config/
  base.mjs
  vue.mjs
  react.mjs
  node.mjs
```

| 配置    | 内容                                            |
| ------- | ----------------------------------------------- |
| `base`  | JavaScript、TypeScript 通用规则和 Prettier 边界 |
| `vue`   | Vue SFC、模板和浏览器环境                       |
| `react` | JSX、React、Hooks 和浏览器环境                  |
| `node`  | Node.js 服务与工程脚本                          |

规则归属：

```txt
所有项目共同遵守   -> base
同类技术栈共同遵守 -> vue、react、node
单个应用需要       -> 应用局部覆盖
```

NestJS 的装饰器和依赖注入可能依赖运行时类型元数据，因此某些类导入不能直接改成 `import type`。这类差异应由 API 应用局部覆盖。

### 2.2 TypeScript 分层

```txt
packages/typescript-config/
  base.json
  app.json
  server.json
```

| 配置     | 内容                             |
| -------- | -------------------------------- |
| `base`   | 严格模式和公共类型安全规则       |
| `app`    | DOM、ES Module、Bundler 模块解析 |
| `server` | Node.js 类型和 Node 模块解析     |

前端应用继承浏览器预设：

```json
{
  "extends": "@supply-chain/typescript-config/app.json"
}
```

NestJS 继承服务端预设，再覆盖装饰器、模块格式和输出目录。根 `tsconfig.json` 通过 project references 汇总全仓检查目标。

配置包解决研发规则复用，不负责浏览器运行时的应用组合。

## 3. 共享包的边界

| 包                  | 封装内容                                    | 消费方             |
| ------------------- | ------------------------------------------- | ------------------ |
| `eslint-config`     | JS、TS、Vue、React、Node 的 ESLint 预设     | 全部工作区         |
| `typescript-config` | 公共、浏览器、服务端 TypeScript 预设        | 前端、后端和公共包 |
| `design-tokens`     | 颜色、圆角、状态色、图表色、主题变量        | Vue 与 React 应用  |
| `ui-vue`            | Vue 组件                                    | 门户、履约中心     |
| `ui-react`          | React 组件                                  | 结算中心           |
| `api-client`        | 请求地址、认证头、JSON 解析、错误处理和重试 | 三个前端应用       |

适合跨框架直接共享：

- 设计变量和视觉语义
- 接口契约
- 框架无关工具
- 请求规范

Vue 与 React 的组件模型和运行时不同，因此分别维护 `ui-vue` 和 `ui-react`。它们可以保持相同的组件语义，不需要共用同一份组件实现。

代码是否进入 `packages`，取决于复用边界是否稳定：

```txt
稳定、无具体业务归属、被多个消费者复用 -> packages
只属于履约或结算的业务规则             -> 对应应用
跨应用运行时协调                       -> 微前端运行时层
最终业务事实                           -> 后端与数据库
```

不要把业务规则集中到含义模糊的 `shared` 包，否则公共包会变成新的单体应用。

## 4. 问题一：多个应用缺少统一入口

当前应用地址相互独立：

```txt
门户       http://localhost:5173
履约中心   http://localhost:5174
结算中心   http://localhost:5175
```

只有链接的门户不能提供统一运行体验。主应用需要负责：

- 统一页面外壳和全局导航
- 应用注册与激活
- 子应用挂载容器
- 全局用户上下文
- 跨应用导航协调
- 加载状态与失败兜底

## 5. 问题二：统一认证与权限

不同端口属于不同 Origin，Local Storage 按源隔离。门户写入的登录信息不会自动出现在两个子应用中。

全局认证上下文可以包含：

```ts
type GlobalContext = {
  user: User | null;
  organization: Organization | null;
  permissions: string[];
  accessToken: string | null;
};
```

职责边界：

```txt
主应用
  -> 登录、Token 刷新、全局退出

子应用
  -> 消费认证上下文
  -> 认证失败时通知主应用
  -> 独立运行时检查登录状态

后端
  -> 最终校验身份、角色、操作权限和数据范围
```

子应用存在两种认证来源：

```txt
嵌入运行
  -> 使用主应用提供的认证上下文

独立运行
  -> 主动检查登录状态
  -> 未登录时跳转统一登录入口
  -> 登录后返回原页面
```

能够打开前端页面，不等于能够读取业务数据或执行业务操作。前端登录检查负责用户体验，后端鉴权才是最终安全边界。

### 5.1 SSO 与老系统

```txt
认证 -> 确认用户是谁
权限 -> 决定用户能做什么
SSO  -> 一次登录，访问多个系统
```

老系统接入统一认证时可能出现三种情况：

| 情况                       | 处理方式                                          |
| -------------------------- | ------------------------------------------------- |
| 已接入同一认证中心         | 认证中心分别向各系统签发可识别的凭证              |
| 可以改造，但凭证或账号不同 | 账号映射、协议适配、Token Exchange                |
| 完全不能改造               | 再次登录、跳转、iframe 保留原运行环境，或后续改造 |

微前端可以组合页面，但不能自动让不同用户体系互相信任。

统一认证后，权限仍由各层分别处理：

```txt
认证中心 -> 证明用户身份
主应用   -> 控制应用入口
子应用   -> 控制业务页面和按钮
后端     -> 最终校验业务权限和数据范围
```

微前端也不要求所有系统共用后端和数据库。不同系统应通过 API、领域事件或聚合服务交换数据，不能直接操作其他系统的数据库。

## 6. 问题三：跨应用业务协同

子应用的业务操作会影响门户指标：

```txt
履约完成       -> 履约完成率变化
异常产生或解决 -> 风险数量变化
结算确认付款   -> 待结算金额变化
```

子应用可以发送“业务数据已变化”的领域事件：

```ts
type DomainEvent =
  | {
      type: "fulfillment:status-changed";
      orderId: string;
      status: string;
    }
  | {
      type: "settlement:status-changed";
      batchId: string;
      status: string;
    };
```

门户收到事件后重新请求最新指标。

跨应用导航需要支持：

```txt
门户发现异常
  -> 打开履约中心的对应订单

履约完成
  -> 打开结算中心的对应任务

结算发现交付差异
  -> 返回履约中心核实
  -> 完成后回到原结算任务
```

主应用或统一通信层应协调应用切换、页面地址和业务上下文。目标应用尚未加载时，导航协议仍需有效。

通信适合传递：

- 发生了什么
- 哪个实体发生变化
- 导航目标
- 必要的 ID 和筛选条件

完整订单和结算数据不应长期复制到前端全局状态。

```txt
前端通信层       -> 通知变化、传递必要上下文
后端接口与数据库 -> 保存最终业务事实
```

## 7. 问题四：全局状态归谁管理

| 状态             | 归属       | 原因                 |
| ---------------- | ---------- | -------------------- |
| 用户、组织、权限 | 主应用     | 整个系统的身份上下文 |
| Token 状态       | 主应用     | 需要统一刷新和失效   |
| 主题、语言       | 主应用     | 影响全部应用         |
| 当前业务域       | 主应用     | 决定激活哪个子应用   |
| 履约筛选条件     | 履约子应用 | 只影响履约页面       |
| 结算表格状态     | 结算子应用 | 只影响结算页面       |
| 完整业务数据     | 后端       | 属于最终业务事实     |

判断标准：状态是否代表整个系统的共同上下文，是否需要唯一所有者。

共享 `design-tokens` 只能统一视觉契约。不同 Origin、Shadow DOM 或 iframe 中的主题变化，还需要定义首次下发和变化广播协议。

## 8. 问题五：主路由与子路由

履约中心使用 History Router，结算中心使用 Hash Router。嵌入主应用后需要处理：

- 主应用用什么路径激活子应用
- History 子应用的路由 `base`
- Hash 地址与 `location.pathname` 的关系
- 菜单和面包屑同步
- 跨应用详情地址
- 深层地址刷新时的服务器回退
- 浏览器前进、后退的响应边界
- 子应用重新进入时的内部地址恢复

职责边界：

```txt
主应用路由 -> 决定进入哪个业务域
子应用路由 -> 决定业务域内部显示哪个页面
```

## 9. 问题六：独立运行与嵌入运行

子应用接入主应用后，仍需支持独立开发、测试和部署。

### 9.1 页面外壳

```txt
独立运行
  -> 显示完整品牌区、导航和顶部栏

嵌入运行
  -> 主应用提供系统级外壳
  -> 子应用隐藏重复布局
  -> 保留业务内容和必要的业务域内部导航
```

业务页面可以保持不变，变化的是应用级布局。

### 9.2 运行入口与生命周期

```txt
独立运行
  -> 自己创建应用并挂载根节点
  -> 准备最小运行上下文

嵌入运行
  -> 主应用调用 bootstrap、mount、unmount
  -> 使用主应用提供的容器、路由前缀和全局上下文
```

子应用改造需要解决：

- 识别当前运行方式
- 避免独立入口与生命周期入口重复挂载
- 挂载到主应用提供的容器
- 卸载 Router、事件、定时器和框架根实例
- 兼容不同部署地址的静态资源路径
- 允许主应用跨域加载开发资源

## 10. 问题七：共享与隔离

```txt
design-tokens -> 跨框架视觉变量和主题协议
ui-vue        -> Vue 组件
ui-react      -> React 组件
api-client    -> 请求约定
```

需要区分：

1. Vue 和 React 可以统一组件语义，不必强行共享组件运行时。
2. `workspace:*` 只解决仓库依赖复用，不保证生产环境只加载一份依赖。
3. 设计变量解决视觉一致，样式隔离防止应用互相污染。

运行时需要检查：

- 全局选择器是否污染其他应用
- Tailwind 基础样式是否重复注入
- 同名 class 是否互相覆盖
- 弹窗和浮层是否挂载到正确容器
- CSS 加载顺序是否改变页面结果

## 11. 问题八：失败与部署治理

一个子应用失败不应拖垮整个门户。主应用需要提供：

```txt
加载中
加载超时
加载失败
重试
降级提示
异常记录
```

失败类型包括：

- 资源下载失败
- 生命周期执行失败
- 业务接口失败
- 子应用卸载不完整
- 新版本发布失败

独立部署还需要处理资源地址、缓存、版本兼容和回滚。

## 12. 微前端改造清单

| 当前问题                     | 需要的能力                         |
| ---------------------------- | ---------------------------------- |
| 多个地址、多个入口           | 主应用外壳、应用注册和激活规则     |
| 登录态无法跨 Origin 自动共享 | 认证上下文、通信协议、独立运行兜底 |
| 子应用操作后门户数据不更新   | 领域事件、数据失效和重新请求       |
| 履约与结算无法连续操作       | 主应用协调的跨应用导航             |
| History 与 Hash 并存         | 主子路由边界、base 和地址恢复      |
| 主题只影响当前页面           | 首次下发和变化广播                 |
| 子应用只有独立入口           | `bootstrap`、`mount`、`unmount`    |
| 样式可能互相影响             | 样式约束与隔离                     |
| 加载失败缺少统一反馈         | 错误捕获、重试与降级               |
| 应用需要独立发布             | 资源路径、版本、缓存与回滚         |

## 13. 启动与验证

自动初始化数据库并启动：

```bash
pnpm install
pnpm bootstrap
pnpm dev
```

手动导入演示数据时：

```bash
pnpm db:up
pnpm dev
```

后端启动成功后，通过数据库工具执行：

```txt
database/demo-data.sql
```

不要同时执行自动初始化和手动数据导入。

访问地址：

```txt
门户       http://localhost:5173
履约中心   http://localhost:5174
结算中心   http://localhost:5175
Swagger    http://localhost:3000/api/docs
```

工程检查：

```bash
pnpm check
pnpm build
```

项目使用 `synchronize: true` 自动创建数据表。生产环境通常关闭自动同步，改用经过审查的数据库迁移脚本。

PostgreSQL 数据保存在 Docker 具名卷中。删除容器不会自动删除数据卷；`docker compose down -v` 会删除数据卷，不应在需要保留数据时执行。

固定容器名：

```txt
supply-chain-postgres
```

常用命令：

```bash
docker start supply-chain-postgres
docker stop supply-chain-postgres
docker logs -f supply-chain-postgres
```

## 14. 核心结论

1. Monorepo 统一源码、依赖和研发规范，不会自动组合浏览器运行时。
2. 配置包应在出现多个真实消费者后提取，抽象来自稳定复用。
3. 主应用负责应用激活、全局上下文、跨应用导航和失败兜底。
4. 统一登录需要唯一状态所有者和更新协议，不能只复制 Token。
5. 子应用独立运行时也要检查认证，后端负责最终鉴权。
6. 通信传递变化通知和必要上下文，最终业务事实由后端维护。
7. 系统级状态归主应用，页面级状态归子应用。
8. 子应用需要同时支持独立运行和嵌入运行，并完整清理副作用。
9. 路由、样式、依赖、失败、版本和部署都属于微前端治理范围。
